# v0.3 Package Separation Design

**Status:** Approved design

**Target release:** 0.3.0

**Depends on:** [Browser-first v1 production roadmap](./2026-08-12-browser-v1-production-roadmap-design.md) and the completed [0.2.0 correctness review](../../reviews/2026-08-12-0.2-core-correctness-review.md)

## Purpose

Version 0.3.0 turns the current single `sip-worker` package into three real,
independently publishable npm packages without changing SIP behavior:

```text
@sip-worker/core
       ↑
       ├── sip-worker
       └── @sip-worker/node
```

The split makes `sip-worker` a browser-first SDK, makes Node support optional,
and gives the shared SIP implementation an enforceable environment-neutral
boundary. It is an architectural migration, not a media or protocol feature
release.

## Decisions

- Use npm workspaces with physical package directories.
- Publish `@sip-worker/core`, `sip-worker`, and `@sip-worker/node` at `0.3.0`.
- Keep the three versions synchronized throughout the pre-1.0 period.
- Use exact `@sip-worker/core` dependency version `0.3.0` in both adapter packages.
- Retain ESM and CommonJS exports for all packages.
- Make a clean Node import break: do not retain `sip-worker/transport/node`.
- Preserve ordinary browser root imports such as `UserAgent` from `sip-worker`.
- Keep `@sip-worker/core` external in browser and Node builds so there is only
  one installed runtime copy and shared class identity is preserved.
- Do not change signaling behavior, add WebRTC, or add reconnection policy.

## Alternatives Considered

### Physical npm workspace packages — selected

Move source into `packages/core`, `packages/browser`, and `packages/node`, with a
manifest, TypeScript project, build, tests, and tarball for each package. This
requires the most mechanical relocation, but package manifests, TypeScript,
bundlers, and tests can all enforce the intended dependency graph.

### One source tree with three build configurations — rejected

This reduces file movement but leaves the runtime boundaries as conventions.
A new relative import can silently draw Node code into a browser build, and
package ownership remains unclear.

### Thin publishing facades over one internal package — rejected

Facades make class identity easy to preserve, but they do not create a true
architecture split. Consumers and maintainers would still need to understand a
single mixed-runtime implementation.

## Repository Layout

The root becomes a private orchestration workspace:

```text
sip-worker/

├── tsconfig.base.json
├── tsconfig.json
├── vitest.config.ts
├── packages/
│   ├── core/
│   │   ├── package.json
│   │   ├── tsconfig.json
│   │   ├── tsup.config.ts
│   │   ├── README.md
│   │   ├── src/
│   │   └── test/
│   ├── browser/
│   │   ├── package.json
│   │   ├── tsconfig.json
│   │   ├── tsup.config.ts
│   │   ├── README.md
│   │   ├── src/
│   │   └── test/
│   └── node/
│       ├── package.json
│       ├── tsconfig.json
│       ├── tsup.config.ts
│       ├── README.md
│       ├── src/
│       └── test/
├── test/
│   ├── browser-bundle/
│   ├── compatibility/
│   └── package/
└── docs/
```

The root manifest has `"private": true` and `"workspaces": ["packages/*"]`.
It is never published. Root scripts orchestrate workspace scripts and the
cross-package acceptance gates.

`tsconfig.base.json` contains shared strict compiler options. The root
`tsconfig.json` is a solution file with an empty `files` array and project
references to all three packages. Core is built before browser and Node.

Tests move with the package that owns the behavior. Cross-package installation,
class-identity, bundle, and compatibility tests stay under the root `test/`.

## Package Ownership

### `@sip-worker/core`

Core owns the current environment-neutral implementation:

- `messages` and `stream`
- transport interfaces and ingress, but no concrete browser or Node adapter
- `transactions` and `dialogs`
- Digest `auth`
- `ua`, including `UserAgent`, registration, and call state machines
- environment-neutral reliability interfaces and SIP OPTIONS liveness
- media protocol, controller, and the current stub handler
- worker bridge protocol, runtime, and supervisor abstractions
- stable error codes and error classes

Worker and media abstractions remain in core because they operate on injected
ports and clocks rather than accessing a global `Worker`. Importing them must
not construct a worker, socket, timer, or media device.

Core source cannot import or access:

- `node:*` modules
- `window`, `document`, `navigator`, or global `WebSocket`
- global `Worker`, `MessagePort`, or `RTCPeerConnection`
- ambient timers or crypto APIs

Environment capabilities continue to enter through explicit interfaces such as
`Transport`, `Clock`, worker ports, and media ports.

Public exports:

```text
@sip-worker/core
@sip-worker/core/messages
@sip-worker/core/stream
@sip-worker/core/transport
@sip-worker/core/transactions
@sip-worker/core/dialogs
@sip-worker/core/auth
@sip-worker/core/ua
@sip-worker/core/media
@sip-worker/core/reliability
@sip-worker/core/bridge
```

### `sip-worker`

The unscoped package is the browser product package. In 0.3.0 it owns the
existing browser WebSocket transport and presents the browser-facing API. Real
WebRTC and browser lifecycle integration remain Milestone 3 and 4 work.

Its root re-exports the commonly used core API, including `UserAgent`, public
event and option types, transport contracts, and stable errors. These are direct
re-exports from `@sip-worker/core`; the browser bundle must not compile a second
copy of core.

Public exports:

```text
sip-worker
sip-worker/transport
```

`sip-worker/transport` exports `BrowserWebSocketTransport` and its public
options/socket interfaces. Browser consumers needing low-level protocol modules
import their documented subpaths from `@sip-worker/core`.

The browser package cannot import `node:*` or `@sip-worker/node`. It cannot read
browser globals at module evaluation time. A WebSocket capability is supplied
when a transport is constructed or connected, matching the current injectable
socket boundary.

### `@sip-worker/node`

The optional Node package owns:

- UDP transport
- TCP transport
- Node WebSocket transport
- native WebSocket Ping/Pong liveness
- Node-specific adapter types

Public exports:

```text
@sip-worker/node
@sip-worker/node/transport
@sip-worker/node/reliability
```

Node depends on core interfaces and errors. It must not copy or reimplement the
codec, ingress, transactions, dialogs, authentication, registration, call state
machines, media state, or worker supervision.

## Dependency and Import Rules

The allowed production graph is:

```text
@sip-worker/core       -> no workspace package
sip-worker             -> @sip-worker/core@0.3.0
@sip-worker/node       -> @sip-worker/core@0.3.0
```

Browser and Node may share development tools at the private workspace root, but
must not depend on each other. Production source uses public core package imports
rather than cross-package relative paths.

The browser and Node builds mark `@sip-worker/core` external for ESM and
CommonJS. This prevents duplicate class definitions and ensures that, within a
module system:

```ts
import { SipError as BrowserError } from 'sip-worker';
import { SipError as CoreError } from '@sip-worker/core';

BrowserError === CoreError;
new BrowserError(0, 'x') instanceof CoreError;
```

The same identity contract is tested with `require()` in CommonJS. ESM and
CommonJS are separate module graphs, so the design does not promise identity
between an ESM constructor and a CommonJS constructor in the same process.

## Build and TypeScript Model

Each package owns a `tsup` configuration and emits:

- ESM `.js`
- CommonJS `.cjs`
- ESM declarations `.d.ts`
- CommonJS declarations `.d.cts`
- source maps

Every package manifest uses an explicit `exports` map, `files` allowlist,
`sideEffects: false`, and the existing Node engine floor of Node 20 where
applicable. The browser manifest does not declare a Node engine requirement.

TypeScript project references express the same graph as package dependencies.
The packages use the root strict configuration and `NodeNext` resolution.
Project builds use `tsc --build`; packaging continues to use `tsup`.

The core compiler project excludes DOM libraries. Browser adapter tests may use
the minimum DOM types needed for WebSocket interfaces. Node uses Node types.
This separation makes an accidental environment dependency a type error before
the bundle audit runs.

## Runtime Behavior and Errors

The package move must preserve the v0.2 signaling behavior and public error
taxonomy. Adapters pass core errors through when possible and do not wrap them
solely because a package boundary was crossed.

Importing any public entry point must not:

- create a socket, worker, timer, or media object
- register a global event listener
- modify `globalThis`
- read an unavailable environment global

Environment validation occurs during adapter construction or connection. All
existing lifecycle settlement, observer isolation, registration refresh, and
resource-baseline guarantees remain required.

## Migration Contract

This is a clean pre-1.0 split. There is no compatibility export for
`sip-worker/transport/node` and no package-level deprecation shim.

The migration guide contains this exact mapping:

| Before 0.3.0 | 0.3.0 |
|---|---|
| `sip-worker` for `UserAgent`, errors, and common browser API | `sip-worker` |
| `sip-worker/messages` | `@sip-worker/core/messages` |
| `sip-worker/stream` | `@sip-worker/core/stream` |
| `sip-worker/transactions` | `@sip-worker/core/transactions` |
| `sip-worker/dialogs` | `@sip-worker/core/dialogs` |
| `sip-worker/auth` | `@sip-worker/core/auth` |
| `sip-worker/ua` | `@sip-worker/core/ua` or browser root `sip-worker` |
| `sip-worker/media` | `@sip-worker/core/media` |
| `sip-worker/bridge` | `@sip-worker/core/bridge` |
| browser part of `sip-worker/reliability` | `@sip-worker/core/reliability` |
| `sip-worker/transport/browser` | `sip-worker/transport` |
| `sip-worker/transport/node` | `@sip-worker/node/transport` |
| Node liveness from `sip-worker/reliability` | `@sip-worker/node/reliability` |

The guide includes installation commands and equivalent ESM, CommonJS, and
TypeScript examples. It explicitly states that v0.3.0 does not add WebRTC or
make a production-browser claim.

## Verification Strategy

### Unit and contract suites

- Existing tests move to the workspace that owns their source.
- The complete v0.2 behavioral suite remains green after relocation.
- One root-owned transport contract is executed against browser WebSocket and
  every Node adapter.
- Core tests run without DOM or Node environment APIs exposed to production
  source.

### Dependency and environment audits

A static graph test parses production imports and rejects:

- `node:*` in core or browser
- `@sip-worker/node` in core or browser
- `sip-worker` in core or Node
- cross-workspace relative imports
- duplicated core-owned implementations in adapter packages

A browser production fixture bundles `sip-worker` with a browser target. It
must build without Node polyfills, and the emitted dependency graph and output
must contain no Node built-in import or require.

An import-safety fixture loads every public entry point with relevant globals
absent or replaced by throwing sentinels. Loading alone must succeed and must
not introduce global keys or observable resources.

### Packed artifacts and compatibility

Each workspace runs `npm pack` into a temporary directory. Gates assert that:

- advertised ESM, CommonJS, and declaration files exist
- only package metadata, README, LICENSE, and allowed build output are included
- no source, test, root configuration, or unrelated package is packed
- all export-map targets resolve

Fresh ESM, CommonJS, and TypeScript fixtures install tarballs rather than
workspace symlinks. A combined compatibility fixture installs all three
`0.3.0` tarballs and verifies:

- browser/core class identity in ESM and CommonJS
- Node/core class identity in ESM and CommonJS
- supported subpath resolution
- a browser-adapter signaling smoke flow
- a Node-adapter signaling smoke flow

The smoke flows exercise current deterministic signaling behavior; they do not
claim external SIP-server interoperability.

### API reports

API Extractor generates one committed report per package. CI regenerates and
compares the reports. Any public API addition, removal, or signature change is
therefore an explicit reviewed diff.

## Release Gates

Milestone 2 is complete only when all of these are true:

1. All three workspace packages are version `0.3.0` with the exact dependency
   graph defined above.
2. Strict project-reference typechecking succeeds.
3. All relocated unit, integration, and deterministic lifecycle tests pass.
4. The shared transport contract passes for browser and Node adapters.
5. Core and browser dependency audits find no Node built-in or forbidden
   workspace import.
6. A production browser bundle builds without Node polyfills.
7. Every public entry point passes the import-side-effect audit.
8. Clean ESM, CommonJS, and TypeScript consumers install and use each tarball.
9. The combined packed-package fixture passes resolution and class-identity
   checks for both module systems.
10. API reports match the reviewed 0.3.0 surface.
11. The migration guide documents every removed or moved 0.2 import.
12. The root documentation continues to describe the library as pre-1.0 and
    signaling-only.

No gate may be skipped, replaced with a source-tree import, or represented by a
placeholder script.

## Out of Scope

- WebRTC, microphone/device management, RTP/RTCP, DTLS, or SRTP
- browser reconnection, network-change, or page-lifecycle policy
- TLS/SIPS/WSS deployment policy
- Asterisk, FreeSWITCH, Kamailio, SIPp, or SIP.js interoperability
- automatic DNS resolution beyond the current explicit Node UDP contract
- protocol changes unrelated to the move
- a softphone UI
- ESM-only migration
- independent package version drift before 1.0

## Completion Evidence

The milestone ends with a dated review document recording the exact commands,
versions, test counts, tarball names, bundle audit result, API-report result,
and implementing commits. The review may authorize Milestone 3 only when every
release gate passes from packed artifacts.
