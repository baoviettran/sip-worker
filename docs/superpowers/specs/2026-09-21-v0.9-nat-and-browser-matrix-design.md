# v0.9 Workstream 4 — NAT Shapes and Browser Matrix Design

**Date:** 2026-09-21
**Status:** Draft for review
**Base:** Workstream 4 of the v0.9 interoperability design
([`2026-08-20-v0.9-interoperability-design.md`](2026-08-20-v0.9-interoperability-design.md#workstream-4--nat-and-browser-matrix))
and Milestone 5 of the browser v1.0 production roadmap
([`2026-08-12-browser-v1-production-roadmap-design.md`](2026-08-12-browser-v1-production-roadmap-design.md)),
whose gate names "the current and previous stable Chrome, Edge, and Firefox,
plus current Safari on macOS".

## Purpose

Close the last evidence gap of v0.9. Two claims in the milestone gate are
currently unproven rather than false:

1. **The three NAT shapes are not each proven.** Direct and STUN-assisted media
   legs already exist in the browser-media suite (built in v0.5), but the STUN
   leg's assertion only proves the harness's STUN responder was *pinged*
   (`test/browser-media/two-way-audio.spec.ts:69-72`); the gathered candidate
   types are `console.log`ged (`:73-75`), never asserted. A call that gathered a
   server-reflexive candidate and then selected a host pair passes today.
2. **The browser matrix does not exist.** The three engines in
   `playwright.config.ts:43` are Playwright's own bundled builds at whatever
   revision the pinned Playwright ships; no Chrome or Edge row exists, and no
   previous-stable row exists for any engine. The matrix the roadmap promises is
   published for no release.

The gate closes when every supported engine/version row runs the media and
controls suites on CI-owned infrastructure, each row's build is pinned and
asserted to report the version it was pinned to, the three NAT shapes each carry
a load-bearing assertion, and no row can pass by being absent or by skipping.

## Scope

### In scope

1. A committed **row table** naming every engine row, its provision pin, and the
   version it must report.
2. A **provisioner** that installs a row's build and verifies the binary reports
   the pinned version, with four verified provision kinds.
3. A **row-driven Playwright config** that reuses the existing media and
   controls specs and web servers unchanged — rows change the engine, never the
   suite.
4. **STUN-leg hardening**: assert the reflexive candidate the library gathered
   is the mapping the STUN server actually observed.
5. A **matrix report** artifact plus a completeness gate that fails when an
   expected row is missing.
6. Extension of `browser-media.yml` into a row matrix with a bounded PR slice and
   a full nightly run.

### Out of scope

- **Driving upstream Firefox.** Playwright cannot: its Firefox is a patched
  build speaking its own protocol. The runner's stock Firefox is 155; the only
  driveable builds are 153 (Playwright 1.62) and 151 (Playwright 1.61). The
  Firefox rows are therefore *Playwright's build at the pinned Playwright
  release* and are labelled that way in the published report — a documented
  proxy, not a silent substitution.
- **Consolidating the two STUN responders.** `test/browser-media/server.mjs`
  deliberately answers with `127.0.0.2` and the observed *port*, because its two
  peers are same-realm and would otherwise prune the reflexively-mapped
  candidate; the interop harnesses (`test/matrix-shared/stun.ts`) report the
  observed *address* because their remote peer is a real PBX that must route
  connectivity checks back. The two have genuinely different correctness
  requirements; merging them would break one to tidy the other. This is recorded
  so neither is "fixed" into the other's bug.
- **Expanding the forced-TURN relay leg to every row.** Relaying is
  engine-agnostic and the leg already proves it on three engines; a per-row
  expansion would cost one coturn container per row for no new claim. Direct and
  STUN coverage does extend to every row for free, because both live in the
  media suite the rows run.
- **Pinning Safari.** The macOS runner provides Safari; the row records the
  version it observed. Pinning it is not possible on hosted runners.
- **The `interop.yml` rebuild and docs/toolchain hygiene** — separate v0.9
  workstreams (sequencing steps 5 and 7).

## Locked decisions

1. **One driver version carries every row.** Playwright 1.62.0 drives all four
   provision kinds by `executablePath`; no second pinned `@playwright/test` and
   no per-row driver version. (Verified by spike — see the next section.)
2. **Pins are fixed in-repo and bumped deliberately.** The matrix does not follow
   vendor releases on its own. A vendor bump is a commit that changes the table
   and the expected-version assertion together.
3. **Rows are parallel CI jobs, not sequential projects in one job.** Today's
   `workers: 1` serialisation would otherwise blow the job timeout as rows are
   added.
4. **The PR slice does zero vendor downloads.** It runs the bundled rows only;
   the vendor rows run nightly and on push to main.
5. **Fail-not-skip at three levels**: the provisioner exits non-zero when a
   build cannot be installed or reports the wrong version; a normal (never
   skipped) in-suite test asserts the observed browser version; and a publisher
   job fails when an expected row's report is absent.
6. **A row's launcher is the pinned binary, never whatever the runner happens to
   have.** The runner image's preinstalled Chrome (152.0.7977.82) and Edge
   (152.0.4191.66) are the *previous* stable milestones; they are not used as
   the current rows.

## Verified by spike (2026-09-21)

Each provision kind was exercised against Playwright 1.62.0: launch, report
`browser.version()`, evaluate JavaScript in the page, and begin ICE gathering.

| Kind | Build exercised | Observed version | Result |
| --- | --- | --- | --- |
| `cft` | Chrome for Testing 152.0.7977.82 (previous milestone) | `152.0.7977.82` | launches, drives, gathers |
| `pw-firefox` | Playwright CDN firefox rev 1532 | `151.0` | launches, drives, gathers |
| `edge-deb` | Edge 152.0.4191.66, `dpkg-deb -x` extracted | `152.0.4191.66` | launches, drives |
| `bundled` | Playwright chromium rev 1234 (control) | `151.0.7922.34` | launches; same ICE state as `cft` |

Two findings the design depends on:

- **Playwright's bundled chromium is itself a CfT build** (same
  `chrome-linux64/chrome` layout, version `151.0.7922.34`), so a CfT row needs no
  special launch handling — only a pin and an `executablePath`.
- **The spike host cannot complete ICE for *any* engine**, bundled-current and
  previous-stable alike (`ice=new`/`failed` for both, identically). The failure
  is environmental, not a driver/build mismatch — established by the
  bundled-current control, which fails the same way. Consequence: **row
  behaviour and the hardened STUN assertions can only be verified on the CI
  runner.** Every implementation task that touches them carries a "verify at
  first run" note, following the existing plan idiom.

Revision-to-version mapping is not linear and must never be assumed:
firefox rev 1538 → `153.0`, rev 1532 → `151.0`. Each row therefore carries the
pin (what is fetched) **and** the expected version (what must be reported) as
separate fields.

## Architecture

### 1. Row table — `test/browser-matrix/rows.mjs`

The single source of truth, read by the provisioner, the Playwright config, and
the integrity test. Plain ESM so every consumer reads it without a build step
(the same reason `test/matrix-shared/playwright-config-guard.mjs` is `.mjs`).

```js
{
  id: 'chrome-previous',
  engine: 'chromium',            // selects the device profile and browserType
  provision: { kind: 'cft', pin: '152.0.7977.82' },
  expectedVersion: '152.0.7977.82',
  label: 'Chrome (previous stable)',
  triggers: ['nightly', 'main'], // the PR slice omits this row
}
```

Invariants the table must satisfy, each one a test case:

- every row id is unique and kebab-case;
- `engine` is one of `chromium`, `firefox`, `webkit`;
- every row has both a `provision.pin` and an `expectedVersion` — for `bundled`
  the pin is the engine revision and the expected version is the version that
  revision reports;
- the PR slice is a strict subset of the full set, and every PR row is
  `bundled` (decision 4);
- the full set contains exactly one row per engine per stability label;
- **each `bundled` row's pin matches what the pinned Playwright actually ships**
  — its revision in `playwright-core/browsers.json` and the version that revision
  reports. A Playwright bump must therefore fail loudly as a deliberate table
  change, instead of silently re-labelling the matrix: without this, bumping
  Playwright would move three rows' engines while the table still claimed the old
  versions, and the rows would fail at the version assertion for the wrong
  reason (or, worse, be "fixed" by pasting the new versions in without notice).

### 2. Provisioner — `test/browser-matrix/provision.mjs`

`node test/browser-matrix/provision.mjs <row-id>` installs the row's build into
a per-run cache directory and prints the absolute executable path on stdout.
Exit code 0 means "installed **and** the binary reports `expectedVersion`".

| Kind | Source | Extracted layout |
| --- | --- | --- |
| `bundled` | Playwright's cache (`~/.cache/ms-playwright`) | no path printed — no `executablePath` is set, Playwright resolves its own build |
| `cft` | `https://storage.googleapis.com/chrome-for-testing-public/<pin>/linux64/chrome-linux64.zip` | `chrome-linux64/chrome` |
| `pw-firefox` | `https://cdn.playwright.dev/dbazure/download/playwright/builds/firefox/<pin>/firefox-ubuntu-24.04.zip` | `firefox/firefox` |
| `edge-deb` | `https://packages.microsoft.com/repos/edge/pool/main/m/microsoft-edge-stable/microsoft-edge-stable_<pin>-1_amd64.deb`, unpacked with `dpkg-deb -x` (no sudo) | `opt/microsoft/msedge/msedge` |

Every URL template above was fetched during the spike. The provisioner verifies
the version **before** returning, so a mis-pinned row fails at provision time
with the URL and both versions in the message, rather than midway through a
suite. It never falls back to a runner-installed binary: an unavailable vendor
artifact is a failed release prerequisite.

### 3. Row-driven config — `test/browser-matrix/playwright.config.ts`

Builds one project per row named by `MATRIX_ROWS` (comma-separated row ids):

- `testMatch` covers the two existing suites plus this tree:
  `/(browser-media|browser-phone|browser-matrix)\/.*\.spec\.ts$/` — the specs are
  reused verbatim, and `test/browser-matrix/version.spec.ts` is what makes the
  version assertion unskippable.
- Device profile by engine: `Desktop Chrome` / `Desktop Firefox` /
  `Desktop Safari`, matching the existing three-engine config.
- `ignoreHTTPSErrors: true` on every project. The rows run the
  controls/recovery suite as well as media, and the phone harness serves a
  per-run CA over HTTPS (`playwright.config.ts:48`, `:64`, `:82`) — a row
  without it fails the phone specs for a reason unrelated to its engine.
- `workers: 1`, one project per CI job, and the existing two `webServer`
  entries.
- The row's job selects its project by name and carries today's exclusion,
  `--grep-invert "forced TURN relay"` (`browser-media.yml:66`). Each row's job
  has no coturn, and the relay spec fails by design when the TURN variables are
  absent — so omitting the exclusion fails every row.
- Launch options move to a shared module (`test/browser-matrix/launch.ts`)
  holding the chromium args, the four Firefox prefs, and WebKit's
  no-autoplay-flag note, each already carrying its explaining comment in the
  current config. Both this config and the existing `playwright.config.ts` import
  it, so the two cannot drift.
- `MATRIX_ROWS` naming an unknown or unselected row **throws**. A silently empty
  project list would report a green run that tested nothing.
- Two failure modes, tested in two different places because they fail at
  different layers: the unknown/unselected-row throw is asserted by the integrity
  test, which can call the row-selection logic offline; an *unprovisionable* row
  (bad URL, truncated download, binary reporting the wrong version) cannot be
  exercised offline, so it is covered by the provisioner's unit tests with the
  network call injected.
- The same two `webServer` entries (4100 media, 4300/4200 phone) and
  `workers: 1`, one project per CI job.

The `firefoxUserPrefs` placement trap that shipped twice (fixed in `a420a46`,
gated in `79fb428`) applies here: the guard
`launchOnlyKeysUnderContextOptions` from
`test/matrix-shared/playwright-config-guard.mjs` must be applied to this config
from the new integrity test, and the shared launch module must be passed as a
value (`launchOptions: firefoxLaunchOptions`) — never spread inside
`contextOptions`, which is the shape the guard exists to catch.

### 4. Version assertion and report — `test/browser-matrix/version.spec.ts`

A normal test (not a `globalSetup`, which a run can outlive) asserting
`browser.version()` equals the row's `expectedVersion`, and writing
`browser-matrix.json`:

| Field | Source |
| --- | --- |
| `row`, `engine`, `label` | the row table |
| `provision.kind`, `pin`, `expectedVersion` | the row table |
| `observedVersion` | `browser.version()` |
| `suites` | per-suite pass/fail as observed by the reporter |
| `playwrightVersion`, `runnerOs`, `runId`, `url` | the environment |

The report is the artifact the roadmap's "supported browser matrix is published
for every minor and major release" is satisfied by; today that matrix exists
only as CI logs, which is not a publication surface.

### 5. STUN-leg hardening — the media suite

Three assertions, uniform across engines:

1. the library performed at least one valid RFC 5389 binding exchange (today's
   assertion, kept);
2. the library's raw candidate capture contains a `srflx` candidate whose **port
   equals a port the STUN server observed** for that binding — a fabricated
   mapping cannot satisfy this, which is the defect class that cost the
   FreeSWITCH Firefox investigation;
3. the existing connection, RTP-growth, remote-track, and energy assertions are
   unchanged.

Changes this needs:

- `test/browser-media/server.mjs`: record the observed address and port per
  binding and expose them (`/stun-seen` already exists for the raw count; add the
  observation set alongside it). The `127.0.0.2` mapping stays exactly as it is,
  for the reason its own comment gives.
- `test/browser-media/index.html`: report the gathered `srflx` candidates'
  address and port, not only their types — the raw capture that feeds
  `gatheredCandidateTypes` at `:265` (built from `:86`) currently keeps only the
  type.
- `test/browser-media/two-way-audio.spec.ts`: assert (1) and (2) for the `stun`
  scenario, replacing the `console.log` at `:73-75`; and carry an explicit
  comment recording that the **selected pair type is deliberately not asserted**,
  because two same-realm peers always choose host/host — the same reason
  `server.mjs` already documents.

**Verify at first run (carried into the plan):** if any engine prunes the
same-realm reflexive candidate from the raw capture — Firefox's behaviour in this
area is the reason today's assertion is only a binding count — then fall back to
the server-side observation set (non-empty observed ports, per-engine share) and
record the divergence for the spec owner. The binding-exchange proof is never
weakened; only the client-side half of assertion (2) may be replaced.

The harness currently contradicts itself on this point, which is why the first
run has to settle it: `server.mjs:159-163` implies the binding count is needed
because "Firefox prunes a same-realm srflx from the final local-candidate set",
while the responder's own mapping comment (below the XOR construction) says
mapping onto `127.0.0.2` means engines "derive a genuine srflx candidate and keep
it rather than pruning it as identical to host". Whichever the first run proves,
the losing comment is corrected in the same change — a comment that contradicts
the code it sits in is how the next reader gets misled.

## CI structure

| Workflow | Change |
| --- | --- |
| `browser-media.yml` | Gains a `schedule:` (it has none today — push and PR only), a `rows` job that computes the engine matrix from the row table for the event, an `engine` job matrix (one row per job, `timeout-minutes: 40`) selecting its project by row name, and a `publisher` job that merges the Linux rows' reports and **fails if any expected row is missing**. The existing `three-engine` job is replaced by the row matrix; `forced-turn-relay` is unchanged. |
| `safari-media.yml` | Unchanged in behaviour; its run writes the observed Safari version in the same report shape and uploads it. It is a separate workflow on a separate runner, so the `browser-media` publisher cannot merge it — the publication step takes both artifacts, and the Safari row is deliberately outside the publisher's completeness check rather than a row that can silently be absent from it. |
| `ci.yml` | Unchanged. |
| New scripts | `test:browsermatrix:unit` (`vitest run test/browser-matrix/*.unit.test.ts`), `test:browsermatrix:integrity` (`node --test test/browser-matrix/*.test.mjs`), and a `test:browsermatrix` runner for one row locally. New include entries in `vitest.config.ts`. |

Triggers: PR runs the bundled rows only; push to `main` and the new nightly
schedule run the full matrix. Cost, honest about the direction of the trade: each
row job repeats checkout, `npm ci`, the package build, and its engine install, so
the PR slice costs *more* runner-minutes than today's single sequential job (~2×,
three jobs instead of one) while wall-clock drops because the rows run in
parallel and no vendor download happens. The full nightly adds ~700 MB of vendor
downloads and five further rows. Narrowing the vendor rows' suite coverage is the
first lever if the nightly outgrows its budget (see open questions).

**Migration note:** branch protection references check *display names*, and the
rows replace the job whose display name is `Chromium / Firefox / WebKit real
audio`. The new names take the row's `label` (`Chrome (previous stable)`, …), so
branch protection must be updated in the same change that lands the row matrix —
not after, or the required checks silently stop matching anything.

## Error handling, determinism, cost

- A provision failure is a hard failure naming the URL, the pin, and the version
  the binary actually reported.
- A version mismatch fails in-suite; no row can downgrade it to a warning.
- The publisher's completeness check is itself unit-tested against the expected
  row set, so the gate cannot be silently emptied.
- Downloads are per-run, not cached across runs: a poisoned cache cannot pass,
  because the version assertion is the authority regardless of what was
  downloaded. The trade is bandwidth, accepted for the nightly and kept off the
  PR path by decision 4.
- `retries` stays as the existing config has it; every row's assertions are
  deterministic (no timing-dependent candidate-type claims — see the documented
  non-assertion in STUN hardening).
- Firefox rows report a version two majors behind upstream by construction; the
  report's `label` and the published matrix say so, so a reader cannot mistake
  151/153 for the current upstream release.

## Implementation sequencing

Each step is a plan task with its own failing test where one is possible:

1. **Row table + its invariants test** (pure, offline, no network).
2. **Provisioner + unit tests** for URL construction, layout resolution, and
   version-verification semantics (network calls injected, so the tests are
   offline).
3. **Integrity test** applying the config guard to the new config and checking
   the row invariants; new npm scripts; `vitest.config.ts` includes.
4. **Config + version spec + report**, running the bundled rows locally as far as
   this host allows, and the PR slice in CI.
5. **CI rows/engine/publisher jobs**, PR slice first, then the full matrix on push
   to main and nightly. **Verify at first run** for each vendor row, on the
   runner: `chrome-current`, `chrome-previous`, `edge-current`, `edge-previous`,
   `firefox-previous`. The `edge-deb` rows carry a specific known risk: a
   `dpkg-deb -x` extraction does not preserve the setuid bit on Edge's
   `chrome-sandbox`, so those rows may need `--no-sandbox` — or a pinned `apt`
   install of the same version instead of extraction. The local spike launched the
   extracted Edge without it, but the spike host is not the runner and this is
   exactly the class of difference the first run exists to catch.
6. **STUN hardening**, with its verify-at-first-run fallback.
7. **Safari version record** into the published report.
8. **Publish the matrix** — a `docs/` supported-browser-matrix page generated
   from the report fields, plus the CI documentation update and the branch
   protection change.

## Open questions

- Whether the vendor rows should also run the full controls/recovery suite or a
  bounded media contract. The design runs both, for uniformity; if the nightly
  exceeds its budget, narrowing the vendor rows is the first lever, and it should
  be a recorded decision rather than a silent trim.
- Whether the published matrix is a generated `docs/` file refreshed each release
  or a release artifact only. The report format supports either; the release
  process decides.
