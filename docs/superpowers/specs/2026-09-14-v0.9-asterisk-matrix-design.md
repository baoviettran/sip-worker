# v0.9 Workstream 3b — Asterisk Call Matrix Design

**Date:** 2026-09-14
**Status:** Draft for review
**Base:** Workstream 3 of the v0.9 interoperability design
([`2026-08-20-v0.9-interoperability-design.md`](2026-08-20-v0.9-interoperability-design.md#workstream-3--pbx-call-matrices)),
Milestone 5 of the browser v1.0 production roadmap, and the shipped FreeSWITCH
leg ([`2026-09-09-v0.9-freeswitch-matrix-design.md`](2026-09-09-v0.9-freeswitch-matrix-design.md)).

## Purpose

Close the second half of the v0.9 "PBX call matrices" workstream: prove the
browser `sip-worker` call matrix against a real, self-contained,
docker-provisioned **Asterisk**, with two-way audio verified programmatically
rather than inferred from SIP traces. The milestone gate is explicit —
*Asterisk and FreeSWITCH both pass the supported call matrix* — so 3a's
FreeSWITCH evidence is only half of it.

This workstream carries a second obligation 3a left behind. The shipped
FreeSWITCH harness restates its page step engine once and its RFC 5389 STUN
responder **five times**; a second PBX that copies either would double a known
duplication. The PBX-agnostic core is extracted into `test/matrix-shared/`
first, and Asterisk is built on the extracted core (decision, 2026-09-14).

The gate closes when the same ten-step matrix passes in current Chromium and
Firefox against a pinned Asterisk container, the recorded browser leg analyzes
as non-silent, and no required step can fail by skipping.

## Scope

### In scope

1. A committed, digest-pinned Asterisk docker environment under
   `test/asterisk-matrix/` — a PJSIP `transport-wss` listener, a WebRTC
   endpoint with digest auth and DTLS-SRTP, and an echo dialplan with
   `MixMonitor`.
2. The ten-step call matrix of 3a, re-expressed against Asterisk mechanisms:
   registration, refresh, registration failure, outgoing call with two-way
   audio, incoming call, hold/resume, mute/unmute, RFC 4733 DTMF, remote BYE,
   WSS-drop recovery.
3. Programmatic two-way audio proof on the Asterisk side: the browser sends a
   synthetic tone and measures received energy on the remote stream; Asterisk
   `MixMonitor` captures the browser leg and the node-side WAV RMS pass
   asserts non-silence.
4. **Extraction of the PBX-agnostic harness core** into `test/matrix-shared/`:
   the step engine, the STUN responder, the WAV RMS pass, TLS minting, the
   Playwright glue, and the packed-bundle build script. `page.ts` in each PBX
   tree becomes a thin entry supplying a PBX profile; the FreeSWITCH specs are
   not rewritten.
5. CI: an `asterisk-matrix.yml` mirroring 3a's nightly-gate plus bounded-PR
   slice split. `freeswitch-matrix.yml` is untouched.
6. Integrity gates extended to the new trees — packed-boundary, fail-not-skip
   scenario coverage, TLS-material exclusion, and the committed-tree floor.

### Out of scope

- **FreeSWITCH behaviour changes.** The extraction is a move, not a rewrite;
  the shipped FreeSWITCH suite is what proves it stayed behaviour-preserving.
  Any FS change beyond mechanical relocation is a defect in this workstream.
- **Opus.** The pinned image ships `codec_ulaw/alaw/g722` and no `codec_opus`;
  the Asterisk leg is narrowband PCMU and the interop claim narrows with it
  (locked decision 4).
- **A multi-version Asterisk axis.** One pinned version, matching 3a's
  single-version pin. A version axis is not required by the milestone gate.
- **NAT shapes, previous-stable engines, Safari** — Workstream 4.
- **`interop.yml` rebuild** — sequencing item 5 of the v0.9 design; it gets its
  own plan once the PBX legs give it real jobs.
- **A combined multi-PBX topology** (one workflow, one container, a compose
  file). Two PBXes, two containers, two workflows; sharing happens at the
  harness-code layer, not the process layer.
- **Anything that can report a successful skip** — a skip is a gate failure by
  definition.
- **No production interop claim.** Passing this matrix authorizes v0.9's
  release gate only.

## Locked decisions

1. **Image: `andrius/asterisk:20.7-cert11_debian-trixie`**, digest
   `sha256:5c96c8f7a17688c79452a4a2a56864b4a7570f4c4276fc353db51e38111bb9c3`,
   reporting `Asterisk certified-20.7-cert11`. Verified empirically
   2026-09-14 — module inventory, container boot with a mounted config tree,
   and a live TLS 1.3 WebSocket upgrade (see *Verified environment facts*).
2. **Asterisk 20 LTS, one version.** Asterisk 20 is the long-term-support
   line; a single pinned version matches 3a and keeps the environment claim
   small enough to defend.
3. **Control plane is AMI.** The Asterisk analogue of 3a's FreeSWITCH event
   socket: originate, hangup, contact lookup, and DTMF observation, on
   loopback with a per-run credential. Primary DTMF observation is the AMI
   DTMF event; a dialplan `UserEvent` capture is the recorded fallback if the
   runtime probe shows AMI does not emit DTMF events for a WSS/PJSIP channel.
4. **Codec: PCMU.** The image has no Opus module, so the Asterisk leg
   negotiates PCMU and its audio claim is narrowband. This is a different
   reason from 3a's PCMU pin, which was a codec-pairing fix — FreeSWITCH does
   not decode `telephone-event/48000`, so the browser's RFC 4733 tones were
   dropped until the step pinned PCMU/8000 with `telephone-event/8000`.
   Asterisk here has no choice at all. Adding `codec_opus` is a separate
   decision with its own image-build implications and is not smuggled into
   this workstream.
5. **Committed config is the authored minimal set**, mounted over the image's
   read-only `/etc/asterisk`: `http.conf`, `pjsip.conf`, `rtp.conf`,
   `extensions.conf`, `modules.conf`, `logger.conf`. What makes this
   defensible rather than merely small is the boot gate: it asserts the
   resulting state against an **explicit allowlist** — the modules the matrix
   depends on are loaded, the WSS transport is bound, the endpoint/auth/aor
   resolve, AMI authenticates. The gate must not be "the log is clean": the
   pinned image ships one module that fails to load
   (`format_ogg_vorbis.so`, missing `libvorbisenc`) and one benign warning
   (`res_musiconhold`, no classes configured), neither of which touches this
   path. A gate written as "no loader errors" would fail forever and invite
   someone to weaken it. A dependency on an image default that the gate
   reveals gets that file **promoted into the committed set** — the tree grows
   only in response to evidence.
6. **Shared core: extract, don't duplicate.** `test/matrix-shared/` holds the
   step engine, STUN responder, RMS pass, TLS minting, Playwright glue, and
   the bundle build script. Each PBX tree keeps a thin `page.ts` entry and a
   `profile.ts`. The five existing copies of the STUN responder collapse to
   one (decision, 2026-09-14).
7. **The `sip` WebSocket subprotocol is already satisfied.** Asterisk requires
   `Sec-WebSocket-Protocol: sip` on the `/ws` upgrade; the browser transport
   already opens with `['sip']` and rejects any other negotiated protocol
   (`packages/browser/src/transport/ws.ts:93`, `:279`). No library change is
   needed, and the requirement becomes an asserted interop fact rather than an
   accident — FreeSWITCH never exercised it.
8. **Loopback only, `--network host`.** Container runs with host networking and
   binds `127.0.0.1` exclusively, matching 3a. Bridge networking with a
   published port cannot reach a container-loopback bind, so this is a
   correctness requirement, not a preference.
9. **Two-way audio is proven by PBX-side recording plus in-page energy** —
   verbatim locked decision 3 of the v0.9 interoperability design, with
   `MixMonitor` in place of `record_session`.
10. **Packed tarball boundary** — the harness page consumes freshly packed
    `@sip-worker/browser`, never `packages/**/src`.

## Architecture — per-run topology

Loopback only, ephemeral free ports, one container per run:

```
Playwright (Chromium | Firefox)
   │  https page (step-runner)          wss signaling            RTP
   ▼                                   ▼                          ▼
[harness page: packed @sip-worker/browser] ──► Asterisk docker ──► MixMonitor WAV
   │  __runMatrixStep(step, args)          --network host              │
   │   AnalyserNode energy / getStats      8089 wss / 5038 ami          ▼
   └────────────────────────────────────────────────────► node-side rms.ts (non-silence pass)
```

- **Asterisk container**: the digest-pinned image above, `--network host`, all
  listeners on `127.0.0.1`. Global setup health-probes it before any step: a
  failed probe throws, it never skips.
- **Config**: the authored minimal set under `test/asterisk-matrix/ast-conf/`,
  mounted read-only over `/etc/asterisk`, port tokens rendered per run
  (`__WSS_PORT__`, `__AMI_PORT__`) with the same residual-token guard 3a uses.
- **TLS**: per-run minted local CA + leaf, shared by the WSS transport and the
  DTLS-SRTP endpoint; mounted into the container, trusted by the Playwright
  browser context. Ephemeral, never committed — the committed tree contains no
  `.key`/`.pem`, enforced by the integrity gate.
- **Ports and deadlines**: free ports picked before the container starts; every
  container and step wait is deadline-bounded, and a timeout is a failure.

  index.html  server.mjs     harness page + HTTPS page server

test/freeswitch-matrix/      behaviour unchanged
  page.ts                    thin entry supplying the FreeSWITCH profile
  profile.ts                 echo target 9196, inbound-contact rewrite enabled
  (specs, ctl, conf unchanged)

                             extensions, modules, logger)

The step engine is one implementation with a small profile, so a matrix step is
added or fixed once and both PBXes get it. The FreeSWITCH tree keeps its specs, its
`fsctl.ts`, its config and its workflow; the diff against shipped code is
relocation plus a thin entry, and the FreeSWITCH suite is the evidence that the
relocation changed nothing.

## The call matrix

Ten steps, the same matrix 3a defines, each a Playwright test against the
harness page. A missing step, missing fixture, container failure, or assertion
failure is a job failure. The right column names the Asterisk mechanism.

| # | Step | Asterisk mechanism and assertion core |
|---|---|---|
| 1 | register (digest 401→200) | PJSIP endpoint/auth/aor over WSS; `registrationState=registered` |
| 2 | registration refresh | Asterisk re-REGISTER before expiry; ≥2 wire REGISTERs, no error records |
| 3 | registration failure (wrong password) | typed `REGISTRATION_FAILED` (401 then final non-2xx, not an auth-budget path) |
| 4 | outgoing call + two-way audio | dial 600 (`Answer` + `Echo`); `MixMonitor` on the leg; page energy above floor on the remote stream; recorded WAV RMS above floor |
| 5 | incoming call | AMI `Action: Originate` to the registered WSS contact (`pjsip show contacts`); `incomingCall` event; answer; `confirmed`; clean hangup |
| 6 | hold/resume | re-INVITE hold/resume transitions; both-direction RTP counter growth asserted after resume and unmute, with growth under hold and mute recorded as evidence rather than asserted (3a's own distinction) |
| 7 | mute/unmute | outbound track `enabled` flips; documented RTP behaviour asserted via getStats |
| 8 | DTMF (`sendDtmf`, RFC 4733) | digit observable at Asterisk via the AMI DTMF event, with the dialplan `UserEvent` capture as the fallback |
| 9 | remote BYE | Asterisk hangs the channel up via AMI `Action: Hangup`; call `terminated` from remote; no error records |
| 10 | WSS-drop recovery | WSS transport severed mid-call; recovery diagnostic emitted; re-register over the restored socket; call re-establishes or fails cleanly with a typed code |

Step 4 is the release-proof step. Step 6 is worth watching for an
interoperability reason rather than a test reason: 3a required a core change to
ignore provisional responses during re-INVITE negotiation
(`packages/core/src/ua/dialog-negotiator.ts`, commit `bc04c67`). Whether
Asterisk sends `100 Trying` on a re-INVITE exercises that fix from the other
direction, and a divergence here is a finding about the fix, not just a test
flake.

## Two-way audio proof

- **Browser → PBX**: the page starts a synthetic oscillator on the call. The
  dialplan runs `MixMonitor` on the answered leg, writing PCM16 WAV; the
  node-side RMS pass asserts a windowed RMS above a per-run calibrated silence
  floor, calibrated from a known-length silence segment recorded in the same
  run rather than a hardcoded constant.
- **PBX → browser**: the echo dialplan returns browser audio; the page
  `AnalyserNode` over the remote stream measures energy over a bounded window
  and getStats counters strictly increase. This side requires the Firefox
  PulseAudio null-sink provisioning already solved in `browser-media.yml`.
- Both directions must pass; a one-way result is a failure.

## Risk retirement

Five things could invalidate the design, and none of them is checkable without
a browser. The plan's first tasks retire them, in this order, before the ten
steps are built:

1. **The container boot gate** (no browser): modules load clean, the WSS
   transport binds, the endpoint resolves, AMI authenticates, and the committed
   tree is sufficient — the fact that decides locked decision 5.
2. **A browser registration over WSS** against Asterisk, through the packed
   harness — the first end-to-end proof that our client and this PBX agree.
3. **A single two-way-audio call** to the echo extension with a recorded,
   non-silent WAV — DTLS-SRTP negotiation and ICE against the browser's mDNS
   `.local` host candidates. 3a needed an in-page STUN responder because its
   PBX rejected `.local` candidates outright; Asterisk's behaviour is unknown
   and the STUN responder is already extracted and available either way.
4. **Inbound originate** to a WSS contact, and **DTMF observation** — the two
   mechanisms with no precedent in 3a.

If any of these fails, the answer is to amend this spec, not to weaken a test:
a softened assertion, a conditional skip, or a step that passes by not running
is a gate failure under the milestone's own rules.

## Determinism and error handling

- Free ports chosen before the container starts; a deterministic committed
  config (loopback binds, conservative timers, no NAT-tuned behaviour).
- Deadline-bounded container start and every step wait; recording flushed
  before the WAV is read; a WAV that is absent or too short throws.
- No audio device, image pull failure, missing config file, insufficient
  committed config, or failed health probe is a hard failure. Fail-not-skip is
  structural: global setup throws and no step is conditionally skipped.
- Artifacts on `always()` for diagnosis: `MixMonitor` WAVs, Asterisk logs, AMI
  transcript, Playwright traces, page console — redacted, no secrets.
- No private key is ever committed: per-run TLS is minted into a temp tree, and
  the integrity gate walks the whole matrix tree for `.key`/`.pem` files.

## CI structure

New workflow **`asterisk-matrix.yml`**, mirroring `freeswitch-matrix.yml`:

| Job | Trigger | Scope |
| --- | --- | --- |
| `asterisk-matrix-pr` | PR | Chromium; every step except the audio-proof step; bounded; fail-not-skip on everything it runs |
| `asterisk-matrix-nightly` | nightly + `workflow_dispatch` | Chromium and Firefox; all ten steps including the recording proof; the v0.9 release gate |

Both jobs: ubuntu runner → PulseAudio null-sink provisioning (Firefox) → mint
TLS → start docker Asterisk with the boot gate → run the matrix → upload
WAVs/Asterisk logs/AMI transcript/traces on `always()`. `freeswitch-matrix.yml`
is not modified by this workstream.

## Local runnability

- `npm run test:astmatrix:unit` — RMS pass, config surface, profile and
  step-runner types, AMI client framing; green with no docker, no browser, no
  audio device.
- `npm run test:astmatrix:infra` — the boot gate against docker Asterisk.
- `npm run test:astmatrix:page` — full local run (Chromium).
- `npm run test:matrix:unit|infra|page` — the FreeSWITCH equivalents, expected
  to stay green unchanged across the extraction.

## Acceptance criteria

1. `npm run test:astmatrix:page` runs all ten steps against docker Asterisk and
   exits 0.
2. The Asterisk nightly workflow (Chromium + Firefox) is green on all ten steps
   and the recorded WAV asserts non-silent; the PR slice is green and bounded.
3. The FreeSWITCH suite — unit, infra, and page — is green **after** the shared
   extraction, with no FreeSWITCH spec file modified and no FreeSWITCH
   behaviour change.
4. One implementation of the step engine and one STUN responder exist in the
   repository; neither is duplicated across the PBX trees.
5. The committed Asterisk config contains no secret and no private key; the
   integrity gate enforces it over the whole matrix tree.
6. The harness imports zero modules from `packages/**/src`.
7. Boot-gate, matrix, and unit tests all pass without an audio device where
   they do not need one, and a missing step or fixture fails CI
   (fail-not-skip is structural and integrity-checked).
8. The exact image digest, package hash, Git commit, and browser versions are
   attached to the run record.
9. No unresolved critical or high-severity review finding remains.

## Open questions

- Whether Asterisk emits AMI DTMF events for a WSS/PJSIP channel, or whether the
  dialplan `UserEvent` capture is required (locked decision 3 records both; the
  probe decides).
- Whether the browser's mDNS `.local` host candidates are acceptable to
  Asterisk's ICE without the in-page STUN responder.
- Whether the boot gate reveals any image-default config file the committed set
  must promote (locked decision 5's growth path).
