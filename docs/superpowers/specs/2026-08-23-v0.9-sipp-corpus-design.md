# v0.9 Workstream 2 — SIPp Protocol Corpus — Design

**Date:** 2026-08-23
**Status:** Draft for review
**Base:** The v0.9 milestone design's Workstream 2
([`2026-08-20-v0.9-interoperability-design.md`](2026-08-20-v0.9-interoperability-design.md#workstream-2--sipp-protocol-corpus))
and the browser-first v1.0 production roadmap
([`2026-08-12-browser-v1-production-roadmap-design.md`](2026-08-12-browser-v1-production-roadmap-design.md)).

## Purpose

Provide protocol-level interoperability and failure evidence for the SIP stack
by running a committed SIPp scenario corpus against the real `UserAgent` from
`sip-worker/node`, in a mandatory fail-not-skip CI job. Protocol evidence comes
before any PBX work (the v0.9 spec's implementation sequencing, step 2).

## Scope

### In scope

1. A versioned, digest-pinned docker SIPp image.
2. Ten committed SIPp XML scenarios covering registration, authentication,
   refresh, outgoing/incoming INVITE, CANCEL races, retransmissions, BYE
   timeout, malformed traffic, timeout, and reconnect behavior.
3. A Node driver that boots `UserAgent` over `NodeUdpTransport` /
   `NodeTcpTransport` from packed tarballs and asserts UA-level outcomes.
4. A per-scenario orchestrator that runs docker SIPp + driver and aggregates
   both exit codes into one verdict.
5. `.github/workflows/sipp.yml`: PR-triggered full corpus plus nightly run;
   no skip paths.

### Out of scope

- RTP/media verification (Workstream 3 energy analysis; Workstream 4 NAT legs).
- WSS transport (SIPp TLS support is weak; the node WS transport is covered by
  existing tests).
- Browser-side scenarios (browser-media / soak suites own those).
- Asterisk/FreeSWITCH matrices (Workstream 3).
- Rebuilding or deleting the legacy skip-based `interop.yml` (v0.9 spec
  sequencing step 5, after Workstreams 2–4 produce real jobs).

## Locked decisions

Decided during brainstorming (user-approved):

1. **Packed tarballs.** The driver consumes freshly packed `@sip-worker/core`
   and `@sip-worker/node` tarballs installed into an isolated fixture
   directory — never `packages/**/src`. Matches the FreeSWITCH pilot's
   constraint: the corpus proves what npm consumers receive, including
   packaging.
2. **UserAgent end-to-end.** Scenarios exercise the full public surface
   (`register()`, `invite()`, `Invitation.answer()`, typed errors), not the
   transaction layer directly. Weak side-only assertions would let a UA with a
   stuck dialog pass; UA-level outcome assertions are the point.
3. **Own workflow now.** WS2 ships `sipp.yml`; the placeholder `interop.yml`
   stays untouched until sequencing step 5.
4. **Signaling-only assertions.** SDP bodies are present where the protocol
   requires them and checked for shape (`v=0`, `m=audio` line), but no RTP is
   exchanged or verified. Media evidence belongs to Workstreams 3–4.

## Architecture

```text
test/sipp/
  scenarios/*.xml        committed SIPp scenario files (the ten-scenario corpus)
  driver/
    agent.ts             boots UserAgent over a chosen node transport; ordered event trace
    assertions.ts        per-scenario expected outcomes -> verdict
    types.ts             ScenarioConfig, ExpectedOutcome, AgentEventRecord
  run-scenario.mjs       orchestrator: <scenario> -> pack, docker SIPp + driver, verdict
  fixtures/              packed-tarball install (created at run time, gitignored)
  README.md              local-run requirements (docker), scenario index
.github/workflows/sipp.yml
```

Per-scenario flow:

1. `npm pack` core + node tarballs into the fixture directory; `npm install`
   them there.
2. The driver child process binds UDP or TCP on an ephemeral loopback port,
   constructs `UserAgent` over `NodeUdpTransport`/`NodeTcpTransport` aimed at
   the loopback SIPp address, and injects a stub media controller (same shape
   as the core soak's) — signaling-only scope.
3. Docker SIPp runs UAS mode (answering the driver's REGISTER/INVITE/BYE) or
   UAC mode (firing INVITE/CANCEL at the driver), loading the committed XML.
4. The driver records UA events into an ordered trace and asserts the
   scenario's expected outcomes.
5. Verdict = SIPp exit code AND driver exit code; either failing fails the
   scenario.

SIPp runs as a short-lived docker container on the same runner (`--network
host`, Linux runners), started and awaited by the orchestrator. No service
containers.

**Why a driver child process:** SIPp needs the driver's port bound before it
fires traffic; the process boundary keeps SIPp's exit code separable from
driver assertions and prevents leaked timers polluting the next scenario.

## Scenario corpus

One XML per scenario, one declarative expectation each, mapping 1:1 to the
v0.9 spec's required surface:

| # | Scenario | SIPp role | What it proves |
|---|----------|-----------|----------------|
| 1 | `register-basic` | UAS | REGISTER → 200; registered state; Contact/Expires handling |
| 2 | `register-auth` | UAS | 401 challenge → Digest-authenticated REGISTER → 200; wrong-password variant → typed `REGISTRATION_FAILED` |
| 3 | `register-refresh` | UAS | Short Expires → re-REGISTER before expiry; stays registered ≥2 refresh cycles |
| 4 | `invite-outgoing` | UAS | INVITE → 180 → 200+SDP → ACK → confirmed; BYE → 200 → terminated |
| 5 | `invite-incoming` | UAC | SIPp INVITEs the driver; `Invitation.answer()` → established; remote BYE → terminated |
| 6 | `cancel-race` | UAC | CANCEL after INVITE before answer → 487 semantics; invitation reaches a cancelled/rejected terminal state; no stuck dialog |
| 7 | `retransmissions` | UAS | UDP: 200 delayed ~2×T1 forces INVITE retransmission; no double-handling; late ACK tolerated |
| 8 | `bye-timeout` | UAS | BYE unanswered → transaction F-timer fires → call terminates anyway |
| 9 | `malformed` | UAS | Garbage bytes / truncated headers → parse-error path surfaces as error event; UA fails cleanly or survives, never crashes uncaught |
| 10 | `reconnect` | UAS | Transport dropped mid-registration → new transport instance + fresh REGISTER restores registration with monotonic CSeq |

Notes:

- Scenario 10 uses the node package's reconnect story (a new transport
  instance per the `Transport` contract); browser lifecycle events do not
  exist on Node.
- Scenario 9 asserts boundedness: parse failure surfaces as a typed error
  event, not an uncaught exception.
- Every scenario is independently runnable:
  `npm run test:sipp -- register-auth`.

## Driver design

Plain TypeScript ESM, Node ≥20, consuming only the packed artifacts plus dev
tooling already in the workspace. All waits bounded — a wait timing out is a
scenario failure, never a hang.

Driver control surface used by the orchestrator: `waitRegistered(timeout)`,
`answerIncomingCall()`, `hangup()`, `waitForCallState(state, timeout)`,
`dispose()`.

Assertion model is declarative per scenario (expected registration sequence,
expected call-state trace, expected typed error codes). On mismatch the driver
prints observed vs expected traces and exits nonzero.

Example (`register-auth`):

```ts
{
  expectRegistrationSequence: ['registering', 'registered'],
  // wrong-credential variant:
  expectRegistrationError: 'REGISTRATION_FAILED',
}
```

## Docker image

Pinned by digest, latest stable SIPp 3.7.x line from `ghcr.io/restcomm/sipp`;
fallback candidate `pbertera/sipp` if it misbehaves. Decision resolved in the
implementation plan's first task by pulling and smoke-testing both, then
pinning the working one. Same invocation locally as CI; local docker is a
documented requirement (`test/sipp/README.md`).

## CI workflow

`.github/workflows/sipp.yml`:

```yaml
on:
  pull_request:
  schedule:
    - cron: '23 6 * * *'   # nightly, off the :00/:30 marks
  workflow_dispatch:
```

Single job: checkout → setup-node 22 (npm cache) → `npm ci` → `npm run build`
→ run all ten scenarios sequentially, fail-fast off so every scenario reports.
No conditional step can exit 0 without running a scenario — missing XML,
docker pull failure, or driver crash is a job failure (fail-not-skip is
structural).

Cost: each scenario ≤30 s wall clock; whole workflow well under 10 minutes.
Nightly is identical to PR — unlike the soak, this suite is inherently short,
so there is no separate bounded slice.

The legacy skip-based `interop.yml` is untouched in this workstream (spec
sequencing step 5 rebuilds/deletes it once WS2–4 land real jobs).

## Error handling, determinism, testing of the infra

**Determinism**

- Ephemeral free ports picked by the orchestrator before both processes start
  (no fixed 5060 contention; parallel-safe).
- Driver waits carry per-scenario deadlines; SIPp scripts use protocol-driven
  branches rather than wall-clock sleeps where possible; retransmissions use
  RFC 3261 T1 = 500 ms defaults with generous tolerances (delays at ~2×T1, not
  1.05×T1) so slow CI runners do not flake.
- Loopback only; the pinned image pull is the sole external dependency (cached
  by CI).

**Failure semantics**

- Orchestrator kills both processes on scenario timeout and reports which side
  failed (driver trace vs SIPp exit code and last responses).
- UA error events are recorded and asserted; nothing swallowed silently.
- An uncaught driver exception is a scenario failure with a stack in the logs.

**Testing of the test infra**

- Vitest unit tests for assertion-matching logic and config parsing
  (`test/sipp/driver/*.unit.test.ts`) — no docker needed, fast PR feedback.
- Orchestrator smoke-checks the docker image presence and hard-fails with a
  clear message when missing — never silent-skip.
- The ten scenarios are themselves the integration tests; no separate
  meta-suite.

## Acceptance criteria

1. `npm run test:sipp` runs all ten scenarios locally against docker SIPp and
   exits 0 on a green stack.
2. Each scenario independently runnable by name.
3. `sipp.yml` runs the corpus on PR and nightly; any missing artifact,
   scenario, or assertion fails the job — no successful skips anywhere.
4. Driver unit tests pass without docker.
5. The driver imports zero modules from `packages/**/src`; this is enforced by
   a grep-style check in CI or a lint rule.
