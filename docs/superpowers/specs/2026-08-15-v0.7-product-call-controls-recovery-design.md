# v0.7 Product Call Controls and Recovery Design

**Date:** 2026-08-15
**Target release:** `0.7.x`
**Starting point:** `0.5.0` real browser WebRTC audio foundation
**Product status after this milestone:** credible internal-beta browser audio SDK, not yet generally production-ready

## Goal

Make the browser package usable by a real softphone application under ordinary
call-control and connectivity conditions. Version 0.7 adds explicit per-call
ownership, mute, hold/resume, RFC 4733 DTMF, bounded WSS and registration
recovery, browser lifecycle integration, stable typed states, cancellation,
deadlines, safe diagnostics, resource counters, and a packed-artifact example.

The milestone preserves the clean package architecture established in 0.3 and
the real-media ownership rules established in 0.5. It does not claim PBX
interoperability certification or general customer-production readiness; those
remain v0.9 and v1.0 gates.

## Success Criteria

Version 0.7 is complete when an application can:

1. Create a browser phone from product-level signaling, account, media,
   recovery, and diagnostics configuration.
2. Connect and register over WSS with bounded, cancellable operations.
3. Receive a call-scoped handle before an outgoing INVITE begins, allowing UI
   subscription and cancellation without global UA methods.
4. Answer, reject, cancel, and hang up incoming and outgoing calls.
5. Mute, hold, resume, send DTMF, and request ICE restart through that handle.
6. Observe separate typed connection, registration, call, signaling, hold, and
   media state without parsing log messages.
7. Recover a registration and, where it can be proven safe, an established call
   after a bounded WebSocket interruption.
8. Fail every unrecoverable operation predictably and release every owned
   resource.
9. Integrate by following a small example that imports only the packed public
   browser package.

## Standards and Compatibility Policy

- SIP signaling follows RFC 3261 transaction and dialog behavior.
- Browser SIP transport remains RFC 7118-compatible WebSocket signaling.
- Hold/resume follows RFC 3264 offer/answer direction negotiation.
- DTMF uses RFC 4733 telephone events through `RTCDTMFSender`.
- ICE restart uses the existing complete, non-trickle SDP re-INVITE path.
- WSS is required by default. Plain WS requires an explicit development-only
  option and must not be accepted silently in a secure production context.
- The v0.5 public methods remain as documented deprecated compatibility wrappers
  during 0.7. No compatibility wrapper may duplicate ownership or state.
- The preferred 0.7 API remains prerelease API and is not frozen under the v1
  semantic-versioning policy until the 1.0 review.

## Package Architecture

```text
@sip-worker/core
  SIP state machines, dialog negotiation, operation lifecycle,
  typed domain errors/events, environment-neutral diagnostics schema
          ^
          |
sip-worker
  BrowserPhone, BrowserCall, reconnect policy, browser lifecycle,
  WebRTC controls, browser diagnostics and example integration

@sip-worker/node
  separate Node transport adapters; consumes shared core contracts only
```

### `@sip-worker/core`

Core owns protocol truth:

- Call and dialog identity.
- INVITE, CANCEL, ACK, BYE, re-INVITE, and in-dialog validation exchanges.
- Local and remote offer/answer sequencing.
- Registration identity and recovery sequencing.
- Operation state, cancellation reconciliation, and stable domain errors.
- Environment-neutral event and diagnostics record types.

Core must not import DOM, WebRTC, browser lifecycle, WebSocket globals, Node
built-ins, ambient timers, or ambient randomness. Deadlines use the injected
clock; jitter uses an injected random source at the browser composition boundary.

### `sip-worker`

The browser package owns environment policy:

- `BrowserPhone`, the application-facing composition root.
- `BrowserCall`, the browser call handle.
- Browser WebSocket creation and resettable socket lifecycle.
- Reconnect scheduling and browser online/offline listeners.
- WebRTC track control, SDP direction application, DTMF sender control, ICE
  state, and peer-connection cleanup.
- Refreshable ICE server acquisition.
- Browser-safe structured diagnostics and resource snapshots.

Importing every public browser entry point must remain side-effect-free and must
not access browser globals. Browser capabilities are resolved at construction or
operation time through explicit environment seams.

### `@sip-worker/node`

Node remains a separate adapter library. It receives only shared core contract
changes required by this milestone. Browser reconnect policy, browser lifecycle,
WebRTC controls, and the example application must never enter the Node package.
Node media readiness does not gate the browser 0.7 release.

## Public Composition Root

`BrowserPhone` is the preferred production entry point. It owns one complete
browser-phone lifecycle and at most one active call.

Public configuration:

```ts
const phone = new BrowserPhone({
  signaling: {
    url: 'wss://sip.example.com/ws',
    reconnect: { initialDelayMs: 250, maxDelayMs: 5_000,
      maxAttempts: 8, recoveryTimeoutMs: 30_000 },
  },
  account: {
    registrarUri: 'sip:example.com',
    aor: 'sip:alice@example.com',
    contact: 'sip:alice@example.com',
    username: 'alice',
    password,
  },
  media: {
    iceServerProvider: ({ signal }) => obtainShortLivedIceServers(signal),
  },
  diagnostics: { logger },
});
```

The public option families and names are fixed by this design:

```ts
interface BrowserPhoneOptions {
  readonly signaling: {
    readonly url: string;
    readonly allowInsecureWebSocket?: boolean;
    readonly reconnect?: Partial<ReconnectOptions>;
  };
  readonly account: {
    readonly registrarUri: string;
    readonly aor: string;
    readonly contact: string;
    readonly username?: string;
    readonly password?: string;
  };
  readonly media?: BrowserMediaOptions & {
    readonly iceServerProvider?: IceServerProvider;
    readonly holdDirection?: 'sendonly' | 'inactive';
  };
  readonly diagnostics?: { readonly logger?: DiagnosticLogger };
}

interface ReconnectOptions {
  readonly initialDelayMs: number;
  readonly maxDelayMs: number;
  readonly maxAttempts: number;
  readonly recoveryTimeoutMs: number;
}

type IceServerProvider = (options: {
  readonly signal: AbortSignal;
}) => Promise<readonly RTCIceServer[]>;
```

The implementation may add documented advanced dependency-injection seams, but
must not rename or weaken these product options. The contracts are:

- Configuration is copied, validated, and made immutable at construction.
- Credentials remain application-owned, memory-only, and non-loggable.
- Retry limits and deadlines are finite, positive, and capped.
- A static ICE server list and an asynchronous provider are mutually exclusive.
- The asynchronous provider is bounded and cancellable.
- The phone owns its transport; application code does not assemble internal
  transaction or media-controller objects.

Reconnect defaults are the values shown above. `Partial<ReconnectOptions>` fills
omitted fields from those defaults. `maxAttempts` counts all socket-open attempts
in one cycle, including the immediate first attempt, and is an integer from 1 to
20. `initialDelayMs` is greater than zero and at most 30 seconds;
`maxDelayMs` is at least `initialDelayMs` and at most 30 seconds;
`recoveryTimeoutMs` is greater than zero and at most 120 seconds. After the
immediate attempt, full-jitter delay is uniformly selected from zero through
`min(maxDelayMs, initialDelayMs * 2 ** (attempt - 1))`.

`username` and `password` must be supplied together or both omitted. A `ws:` URL
is rejected unless `allowInsecureWebSocket` is exactly `true`; setting it cannot
override browser mixed-content enforcement. Supplying both static `iceServers`
and `iceServerProvider` is a construction-time error.

The existing `BrowserUserAgent` remains available as an advanced compatibility
surface. It delegates to the same owners; it must not create a second reconnect,
call, or media state machine.

## Per-Call API

An outgoing call handle exists before dialing starts:

```ts
const call = phone.createCall('sip:bob@example.com');

call.on('stateChanged', ({ state }) => updateUi(state));

await call.start({ signal, timeoutMs: 30_000 });
call.setMuted(true);
await call.hold({ signal });
await call.sendDtmf('123#');
await call.resume({ signal });
await call.hangup({ signal });
```

This two-step construction is intentional. It lets an application subscribe to
state and retain an explicit cancellation owner before the INVITE reaches the
wire. `start()` settles when the call is confirmed, not when bytes are sent.

Incoming calls arrive through the same browser-level handle:

```ts
phone.on('incomingCall', async ({ call }) => {
  await call.answer({ signal });
  // or await call.reject({ statusCode: 486 });
});
```

The public types are distinct: `OutgoingBrowserCall` exposes `start()` and
`cancel()`, `IncomingBrowserCall` exposes `answer()` and `reject()`, and both
extend the shared active-control surface `BrowserCall`. Invalid direction-only
operations are therefore absent at compile time rather than failing at runtime.

The call handle owns:

- Its opaque diagnostic identifier.
- Its SIP dialog owner and session subscriptions.
- Its pending public operations.
- Its browser media session and media subscriptions.
- Its DTMF operation.
- Its terminal cleanup path.

Global v0.5 `bye()` and `restartIce()` methods delegate to the sole active call
and are deprecated. They never search or mutate an independent call registry.

## Orthogonal State Model

State dimensions remain separate so applications never receive ambiguous
combinations.

### Connection state

```ts
type ConnectionState =
  | 'disconnected'
  | 'connecting'
  | 'connected'
  | 'recovering'
  | 'failed'
  | 'disposed';
```

### Registration state

```ts
type RegistrationState =
  | 'unregistered'
  | 'registering'
  | 'registered'
  | 'recovering'
  | 'failed';
```

### Call lifecycle state

```ts
type CallState =
  | 'new'
  | 'establishing'
  | 'established'
  | 'terminating'
  | 'terminated'
  | 'failed';
```

### Call signaling state

```ts
type CallSignalingState = 'stable' | 'recovering' | 'lost';
```

### Hold state

```ts
interface HoldState {
  readonly local: boolean;
  readonly remote: boolean;
}
```

Mute is an independent boolean. Media retains its existing monotonic media
session state unchanged in 0.7. Events contain previous and next values and emit
only on effective change. Listener exceptions remain isolated from committed
transitions.

## Public Event Contract

`BrowserPhone` exposes read-only `connectionState` and `registrationState`
properties and these events:

- `connectionStateChanged` with exact previous and next `ConnectionState`.
- `registrationStateChanged` with exact previous and next `RegistrationState`.
- `incomingCall` with one `IncomingBrowserCall` handle.
- `failed` with a canonical safe error for a phone-level terminal failure.

`BrowserCall` exposes read-only `state`, `signalingState`, `holdState`, `muted`,
`mediaState`, and `remoteIdentity` properties. `remoteIdentity` is an immutable,
size-bounded parsed `{ uri, displayName? }` value intended for application UI;
it is never copied into diagnostics. Call events are:

- `stateChanged`, `signalingStateChanged`, `holdStateChanged`, and `mutedChanged`,
  each carrying exact previous and next values.
- `mediaStateChanged`, `remoteAudio`, and `mediaFailed`, preserving the canonical
  v0.5 media payloads without exposing SDP or ICE details.
- `failed` with one canonical call error.

Every event name has one payload type, every payload is immutable, and every
transition commits before observers run. A throwing observer cannot prevent
other observers, protocol progression, or cleanup. An incoming call received
while another call is owned is rejected with 486 before media acquisition and
never emits `incomingCall`.

## Public Operation Contract

Every cancellable asynchronous public mutation accepts `OperationOptions`.
`dispose()` is deliberately not cancellable because cleanup must run to
completion. `setMuted()` is synchronous.

```ts
interface OperationOptions {
  readonly signal?: AbortSignal;
  readonly timeoutMs?: number;
}
```

Default overall deadlines are 30 seconds for connection, registration,
call-control, DTMF, and media-control operations; call establishment is 120
seconds. A shorter SIP transaction or media deadline wins. Overrides are finite
positive milliseconds capped at 120 seconds. Recovery has its separate 30-second
default deadline. `dispose()` uses a non-configurable 30-second internal bound
for transport close but always completes local cleanup.

Rules:

- Concurrent `connect`, `register`, `unregister`, `hold`, `resume`, `hangup`, and
  `dispose` calls for the same desired state share one promise.
- Conflicting operations fail with `OPERATION_IN_PROGRESS` or `INVALID_STATE`.
- Aborting before transmission prevents the operation.
- Aborting a pending initial outgoing call sends CANCEL and reconciles the INVITE
  final response before ownership is released.
- Aborting an already-sent REGISTER or re-INVITE cannot erase the exchange.
  Internal protocol processing remains owned and bounded, and the eventual
  committed state is emitted even if the caller stops awaiting the operation.
- Timeout and user abort use different stable error codes.
- Remote BYE, transport terminal failure, and disposal preempt call-control
  operations and settle them exactly once.
- `dispose()` is idempotent and all callers share the same completion promise.
  It resolves after local resources reach zero; socket-close failures are
  emitted through safe diagnostics and do not strand or reject cleanup.

Settlement points are fixed:

| Operation | Successful settlement |
| --- | --- |
| `connect` | Current WSS generation is open with SIP subprotocol and ingress installed |
| `register` | Final registration 2xx is processed and refresh is scheduled |
| `start` | INVITE 2xx is processed, remote SDP is applied, ACK is sent, and media is connected |
| `answer` | Local 2xx is sent, ACK is received, and media is connected |
| `reject` | Final rejection is successfully handed to the live transport |
| `cancel` | CANCEL completes and the INVITE final response is ACKed/reconciled |
| `hangup` | BYE final 2xx is processed and local call resources are released |
| `hold` / `resume` | Re-INVITE 2xx, remote SDP, ACK, and local direction commit complete |
| `sendDtmf` | `RTCDTMFSender` reports an empty tone buffer |
| `restartIce` | Re-INVITE completes and ICE returns to connected/completed |
| `unregister` | Unregistration final 2xx is processed and refresh/recovery is disabled |
| `dispose` | All local owners and resource counters have reached zero |

## Reconnect Architecture

Reconnect policy belongs to a browser-owned `ReconnectController`. A
resettable `BrowserWebSocketTransport` creates and owns individual socket
generations but does not schedule policy retries.

The controller guarantees:

- At most one live socket generation and one connection attempt.
- Exponential backoff with full jitter.
- A finite maximum delay, attempt count, and total recovery deadline.
- Deterministic tests through injected clock and random source.
- Generation tokens so stale socket callbacks cannot affect the current state.
- Explicit disconnect, unregister, or dispose suppresses the corresponding
  automatic recovery.
- A terminal failure state after exhaustion; recovery never loops forever.

Browser online/offline events are hints:

- Offline pauses creation of new sockets but does not pause the total recovery
  deadline.
- Online permits an immediate attempt without proving connectivity.
- Actual socket success is authoritative.
- Visibility changes never disconnect signaling or media.
- Page lifecycle events may produce safe diagnostics but cannot promise survival
  across arbitrary browser process suspension.

## Registration Recovery

On unexpected transport loss:

1. Stop ingress for the dead generation.
2. Settle transactions owned by that generation with typed transport errors.
3. Stop registration refresh and mark registration recovering.
4. Reconnect WSS under the bounded controller.
5. Restart ingress for the new socket generation.
6. Restore registration using the stable registration Call-ID and a strictly
   increasing CSeq.
7. Resume refresh only after a successful final registration response.

Refresh, manual register, recovery register, and unregister are serialized by
one registration owner. An explicit unregister wins over pending recovery and
prevents automatic re-registration. Authentication challenges follow the
existing bounded Digest logic; credentials never enter recovery events.

## Call Recovery

An unconfirmed outgoing or incoming call fails on signaling loss. Initial INVITE
transactions are not replayed because doing so could create duplicate calls or
contradict a remote final response.

An established call may retain flowing media during signaling recovery:

```text
established/stable
    -> established/recovering
    -> established/stable
       or terminated/lost
```

After WSS and registration recovery:

- If media remains healthy and no network-change evidence exists, perform a
  bounded in-dialog OPTIONS exchange. An identity-valid 2xx, 405, or 501 final
  proves that the dialog route is live; 408, 481, timeout, transport failure, or
  every other final response fails recovery.
- If ICE disconnected/failed or browser network change requires new candidate
  discovery, perform one serialized ICE-restart re-INVITE.
- A `481` or other definitive dialog-loss response terminates the call.
- A timeout, exhausted reconnect policy, failed re-registration, or failed dialog
  validation terminates locally with `SIGNALING_RECOVERY_FAILED` and releases
  media.

Registration restoration alone never marks a call recovered. The call handle
and its opaque ID remain stable throughout a successful recovery.

## Refreshable ICE/TURN Configuration

Production applications normally use short-lived TURN credentials. Version 0.7
supports either:

- An immutable static `RTCIceServer[]`, preserving v0.5 behavior; or
- An asynchronous provider invoked before a new session and before an ICE
  restart that requires refreshed credentials.

Provider operations receive an abort signal, have a finite deadline, and return
validated defensive copies. Concurrent requests for the same recovery share one
result. Credentials and server details never enter public errors, diagnostics,
or serialization. Failure maps to a canonical media/recovery error and cannot
leave a partially configured peer connection.

## Mute

`call.setMuted(boolean)` changes only the local audio sender:

- It performs no SIP negotiation.
- It is idempotent and emits only effective changes.
- The chosen state survives microphone replacement, hold/resume, ICE restart,
  and signaling recovery.
- It does not affect remote audio playback.
- No active call produces `INVALID_STATE`.

Track replacement applies the stored mute preference before the replacement
becomes observable. Cleanup never re-enables a released track.

## Hold and Resume

Hold/resume uses RFC 3264 direction attributes in an in-dialog re-INVITE.

- Default local hold offer direction is `sendonly`, the conventional SIP hold
  form. The microphone track is disabled so private microphone audio is not
  transmitted.
- An explicit `inactive` policy is available for deployments requiring both
  directions suspended.
- Resume restores `sendrecv` while preserving the user's mute preference.
- Remote `sendonly` and `inactive` offers update remote-hold state correctly and
  produce the matching answer direction.
- Local and remote hold remain independent.
- Desired state is staged; public state commits only after successful SDP,
  final response, and ACK handling.
- Failure rolls media direction and public state back to the last confirmed
  state.

Hold, resume, remote re-INVITE, and ICE restart share the existing dialog
negotiation owner. There is never more than one active offer/answer exchange.
SIP `491 Request Pending` glare receives at most one automatic retry. Following
RFC 3261 section 14.2, the Call-ID owner retries after a uniformly selected
2.1-4.0 seconds; the other endpoint retries after a uniformly selected 0-2.0
seconds. The injected clock and random source make the choice deterministic in
tests. A retry is abandoned on remote BYE, disposal, deadline, or terminal
transport failure.

## DTMF

DTMF uses negotiated RFC 4733 telephone events through `RTCDTMFSender`.

- Accepted symbols are `0-9`, `A-D`, `*`, and `#`.
- Duration and inter-tone gap are finite and validated against WebRTC limits.
- Capability requires both negotiated telephone-event support and an available
  sender with `canInsertDTMF`.
- The operation settles when the tone buffer completes, not when tones are only
  queued.
- Abort clears remaining queued tones where the browser permits and settles the
  operation once.
- A second sequence while one is active rejects with `OPERATION_IN_PROGRESS`;
  there is no unbounded tone queue owned by the library.
- Loss of the sender, call termination, recovery failure, or deadline settles
  the operation with a typed error.

Automatic SIP INFO fallback is forbidden. A later explicit fallback may be
added only with configuration and evidence in the v0.9 PBX matrix.

## Error Taxonomy

The public error taxonomy extends the existing canonical SIP and media errors
with stable codes including:

- `CONNECTION_RECOVERY_EXHAUSTED`
- `REGISTRATION_RECOVERY_FAILED`
- `SIGNALING_RECOVERY_FAILED`
- `OPERATION_ABORTED`
- `OPERATION_TIMEOUT`
- `OPERATION_IN_PROGRESS`
- `HOLD_NEGOTIATION_FAILED`
- `DTMF_UNSUPPORTED`
- `DTMF_FAILED`

Existing codes such as `CONNECTION_FAILED`, `INVALID_STATE`, and canonical media
codes remain canonical rather than being wrapped into duplicate browser-only
classes. Public messages are fixed and safe. A local cause may be retained as a
non-enumerable, non-serialized diagnostic cause, following the v0.5 media-error
pattern.

Errors may expose allowlisted operation name, state, attempt count, and bounded
duration. They must never expose credentials, Authorization headers, full SIP
URIs, user-provided headers, SDP, ICE candidates, IP addresses, device IDs,
device labels, or raw browser exception text.

## Diagnostics

Diagnostics use an injected sink and vendor-neutral record schema:

```ts
interface DiagnosticRecord {
  readonly timestamp: number;
  readonly severity: 'debug' | 'info' | 'warn' | 'error';
  readonly subsystem: 'connection' | 'registration' | 'call' | 'media' | 'lifecycle';
  readonly code: DiagnosticCode;
  readonly connectionId?: string;
  readonly callId?: string;
  readonly context?: Readonly<Record<string, string | number | boolean>>;
}
```

The final schema uses closed unions for subsystem and event code. Context keys
are allowlisted per event, values are bounded, and unknown values are dropped.
Listener exceptions are isolated. The library has no unconditional
`console.log`, `console.warn`, or `console.error` and bundles no monitoring,
analytics, or OpenTelemetry backend.

Applications can adapt records to their chosen telemetry system. Diagnostic
identifiers are locally generated opaque values, not SIP Call-ID, URI, phone
number, username, device ID, or network address.

## Resource Counters and Ownership

`phone.diagnostics.resources()` returns an immutable snapshot of counts only:

- Live socket generations and reconnect attempts.
- Active calls and dialog negotiations.
- Pending public operations and timers.
- Peer connections and local tracks.
- Browser lifecycle and device listeners.

The ownership tree is:

```text
BrowserPhone
|- connection/reconnect controller
|- registration controller
|- browser lifecycle listeners
|- diagnostics
`- BrowserCall
   |- SIP dialog and negotiation
   |- DTMF operation
   `- media session
      |- peer connection
      |- tracks
      `- media listeners
```

Every resource has exactly one owner and one terminal cleanup path. Disposal is
child-first, idempotent, and safe when observers throw. Terminal calls detach
from the phone before application callbacks can create another call. Repeated
connect/register/call/recover/dispose cycles return all counters to baseline.

Counters are diagnostic assertions, not mutable control surfaces. Test-only
methods must not be added to the public API.

## Testing Strategy

### Deterministic tests

- Reconnect backoff, full jitter, attempt caps, total deadline, offline pause,
  online immediate retry, stale socket generations, explicit-disconnect races,
  and disposal.
- Registration refresh/recovery/unregister serialization and CSeq continuity.
- Public operation settlement, abort-before-send, abort-after-send
  reconciliation, timeout, duplicate calls, and conflicting calls.
- State transitions and observer isolation for every state dimension.
- Hold SDP direction, remote hold, rollback, ACK failure, 491 retry, collision,
  BYE preemption, and mute preservation.

  replacement, termination, and timeout.
- ICE provider validation, immutability, refresh, cancellation, timeout,
  redaction, and failure cleanup.

### Real browser acceptance

Required current-engine coverage:

- Chromium.
- Firefox.
- Playwright WebKit.
- Real shipping Safari through the macOS `safaridriver` workflow.

Tests run the built or packed browser artifact and verify:

- Mute stops effective outbound audio while retaining the call.
- Hold/resume changes negotiated direction and restores two-way RTP.
- Real DTMF capability and tone-buffer completion where supported.
- Abrupt WSS loss, reconnection, re-registration, dialog validation, and
  continued or restarted media.
- Offline/online transitions and exhausted recovery.
- Static and refreshed TURN configuration without credential disclosure.

Required jobs have no successful skip path and no `continue-on-error`. A missing
browser, relay, server, or assertion is a failed prerequisite, not a pass.

### Distribution and API gates

- Full typecheck, build, unit, integration, architecture, API-report, bundle,

- Clean packed ESM, CommonJS, and TypeScript consumers compile the preferred
  `BrowserPhone`/`BrowserCall` API and deprecated v0.5 wrappers.
- Browser bundles contain no Node built-ins or import-time browser-global reads.
- The example application builds and runs against the exact packed artifact.
- Documentation links, state tables, error-code lists, migration signatures,

## Release Gate

Version 0.7 must not be called complete unless all of the following are true:

1. Every public operation has an explicit settlement/cancellation/deadline test.
2. Recovery cannot create overlapping socket, registration, dialog, media, or
   timer owners.
3. Registration is restored before established-call recovery can succeed.
4. Established-call recovery validates the dialog or completes a successful ICE
   restart; reopening WSS alone is insufficient.
5. Mute, hold/resume, remote hold, DTMF, and ICE restart pass deterministic and
   packed-browser tests.
6. Repeated recovery cycles return resource counters to their exact baseline.
7. Diagnostic and error redaction scans contain no sensitive fields.
8. Chromium, Firefox, Playwright WebKit, and shipping Safari required jobs pass
   without skip paths.
9. The packed example proves the public integration path.
10. Full `npm run verify` passes from a clean locked dependency tree.
11. A whole-milestone review has no unresolved critical or high-severity
    correctness, security, ownership, packaging, or documentation finding.

## Production Position After v0.7

Passing this milestone makes the package suitable for an internal beta or a
tightly controlled non-customer pilot. It does not by itself authorize general
customer production. The remaining production path is:

1. v0.9: real Asterisk and FreeSWITCH matrices, SIPp failure corpus, broader
   browser/NAT evidence, load testing, and eight-hour soak.
2. v1.0: API freeze, complete operational/security documentation, independent
   security review, exact-tarball staging period, and release-candidate approval.

Claims in README, changelog, package metadata, and release notes must preserve
this distinction.
