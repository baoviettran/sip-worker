# v0.5 Real Browser WebRTC Audio Design

**Status:** Approved design

**Target release:** 0.5.0

**Depends on:** [Browser-first v1 production roadmap](./2026-08-12-browser-v1-production-roadmap-design.md), the completed [v0.3 package-separation design](./2026-08-12-v0.3-package-separation-design.md), and the [v0.3 package-separation review](../../reviews/2026-08-12-0.3-package-separation-review.md)

## Purpose

Version 0.5.0 replaces the fixed SDP media stub with real, two-way browser
audio. It is the first release in which an application can use the browser
package to negotiate a real `RTCPeerConnection`, capture a microphone, receive
remote audio, and operate through direct, STUN-assisted, or TURN-relayed ICE.

This milestone is a production-quality media foundation, not a complete
softphone. Mute, hold, DTMF, automatic network recovery, the final v1 API, and
PBX interoperability certification remain later roadmap milestones. The design
nevertheless requires bounded operations, deterministic ownership, typed
failures, real-browser tests, and no resource leaks.

All three packages move from 0.3.0 to 0.5.0 together under the existing
synchronized pre-1.0 versioning policy. No 0.4 release is required; the roadmap
number identifies the capability milestone.

## Production Contract

The milestone is complete only when all of the following are true:

- Outgoing and incoming SIP calls exchange browser-generated SDP and carry
  measurable two-way RTP audio.
- Browser media code remains outside `@sip-worker/core` and Node code remains
  outside the browser package.
- Microphone, peer connection, remote-track, listener, request, and timer
  ownership has one idempotent cleanup path.
- Permission denial, device failure, SDP failure, ICE failure, timeout,
  cancellation, and unsupported output selection are distinguishable errors.
- Chromium, Firefox, WebKit, and shipping Safari have automated evidence at the
  level defined in this document.
- TURN is exercised as a relay, rather than accepted merely because an
  `iceServers` object was passed to a constructor.
- Fixed/stub SDP is not used by the browser production composition root.

Passing mocked unit tests alone does not meet this contract.

## Decisions

- Add a browser-specific `BrowserUserAgent` composition root; do not subclass
  the core `UserAgent`.
- Keep the existing structured-clone-safe media protocol between the core call
  state machines and browser media implementation.
- Use one `RTCPeerConnection` and one audio `sendrecv` transceiver per call.
- Support one active media call per `BrowserUserAgent` in 0.5.0. Concurrent
  attempts settle predictably instead of creating partially owned media.
- Use non-trickle ICE for initial SIP offer/answer and ICE restart. Wait for ICE
  gathering to complete within a configured deadline before sending SDP.
- Prefer Opus while retaining WebRTC/SIP audio compatibility codecs PCMU and
  PCMA and associated telephone-event capabilities offered by the browser.
- Use `RTCRtpTransceiver.setCodecPreferences()` when supported. Do not use
  brittle text-based SDP codec munging.
- Deliver remote `MediaStream` objects to the application. Do not create or
  autoplay hidden DOM elements.
- Keep TURN credentials application-owned, in memory, and absent from errors,
  logs, and diagnostic events.
- Provide explicit local and remote ICE-restart signaling. Automatic recovery
  policy remains v0.7 work.
- Retain the core stub media handler for deterministic core tests and explicitly
  low-level consumers; it is not the browser default.

## Alternatives Considered

### Browser media behind the core media protocol — selected

`BrowserUserAgent` composes the core `UserAgent`, a `WorkerMediaController`, and
a browser `WebRtcMediaManager` connected by two media-port endpoints. The core
sees only serializable commands and replies. WebRTC objects and media streams
never cross that boundary.

This preserves the environment-neutral core, permits the SIP state machines to
run behind a worker bridge later, and gives tests a deterministic protocol seam.

### Inject WebRTC objects directly into core — rejected

This would make core aware of browser object lifetimes and weaken the package
boundary established in v0.3. It would also make worker separation and
non-browser adapters harder.

### Put SIP and WebRTC into one browser-only UA implementation — rejected

This duplicates orchestration already owned by core and encourages signaling
and media state to diverge. A composition root is sufficient without a second
SIP implementation.

## Architecture and Ownership

```text
application
    |
BrowserUserAgent ---- BrowserMedia facade ---- HTMLMediaElement (app-owned)
    |
core UserAgent
    |
WorkerMediaController
    |
structured media commands/replies
    |
WebRtcMediaManager
    |-- MediaDeviceManager
    |-- WebRtcMediaSession (one per call)
    `-- RemoteAudioRenderer helper
```

### `BrowserUserAgent`

The browser package owns the high-level composition root. It constructs the
media-port pair, controller, manager, and core UA; delegates signaling methods;
forwards core and media events through a listener-isolated typed emitter; and
owns final disposal order.

It accepts core UA options except `mediaController`, plus browser media options.
Supplying a second media controller is not allowed because that would create
ambiguous ownership. The existing low-level core `UserAgent` remains exported
for advanced composition.

### `WebRtcMediaManager`

The manager validates commands, enforces the one-active-session limit, creates
sessions, serializes negotiation, maps browser exceptions to stable errors, and
guarantees cleanup. It depends on an injected browser-media environment for
tests, with production defaults resolved at construction time rather than at
module evaluation time.

The production source may use DOM types but must not touch `navigator`,
`RTCPeerConnection`, or `document` merely by importing `sip-worker`.

### `WebRtcMediaSession`

Each session exclusively owns:

- one `RTCPeerConnection`;
- one local microphone track while active;
- one remote `MediaStream` assembled from received audio tracks;
- peer-connection and track listeners;
- ICE-gathering and negotiation waiters;
- its current negotiation operation.

Session disposal is idempotent. It invalidates pending operations, detaches
listeners, stops every locally and remotely owned track, closes the peer
connection, clears waiters, and emits no later state transition from stale
callbacks.

The application owns only the `HTMLMediaElement` it supplies. A delivered
remote stream is a view of session-owned tracks; applications must not assume
those tracks survive call termination.

### `MediaDeviceManager`

The manager stores only an in-memory preferred microphone device ID. It never
persists device IDs or credentials. `prepare()` requests permission and
validates constraints using a probe stream, then stops the probe immediately.
Starting or answering a call obtains a fresh track.

Device labels and stable IDs may be unavailable before permission is granted;
the API documents that browser privacy behavior. A device-change event prompts
the application to refresh the list. Automatic fallback after unplugging is
deferred to v0.7; an active-track failure in v0.5 is observable and terminal.

## Public Browser API

The milestone adds the following product-facing shape. Exact declaration syntax
may vary only where TypeScript requires it; behavioral meaning is normative.

```ts
const ua = new BrowserUserAgent({
  transport,
  clock,
  registrarUri,
  aor,
  contact,
  idGenerator,
  media: {
    iceServers: [
      { urls: 'turns:turn.example.com', username, credential },
    ],
    iceGatheringTimeoutMs: 8_000,
    mediaOperationTimeoutMs: 30_000,
    audioConstraints: {
      echoCancellation: true,
      noiseSuppression: true,
      autoGainControl: true,
    },
  },
});

await ua.media.prepare({ microphoneDeviceId, signal });
await ua.connect();
await ua.register();

ua.on('remoteAudio', ({ sessionId, stream }) => {
  audio.srcObject = stream;
});

await ua.invite('sip:bob@example.com');
await audio.play(); // application/user-gesture policy remains visible
await ua.bye();
await ua.dispose();
```

Incoming calls no longer expose SDP:

```ts
ua.on('incomingCall', async ({ invitation }) => {
  await invitation.answer();
});
```

`Invitation.answer(localSdp: string)` becomes `Invitation.answer()`. The core
invitation asks its media controller to apply the remote offer and create the
local answer before sending 200 OK. This is an intentional pre-1.0 breaking API
change and must be called out in the migration guide.

The browser media facade exposes:

```ts
interface BrowserMedia {
  listDevices(): Promise<readonly BrowserAudioDevice[]>;
  prepare(options?: PrepareMediaOptions): Promise<void>;
  selectMicrophone(deviceId: string | undefined): Promise<void>;
  attachRemoteAudio(
    element: HTMLMediaElement,
    options?: { readonly outputDeviceId?: string; readonly play?: boolean },
  ): Promise<() => void>;
  setAudioOutput(element: HTMLMediaElement, deviceId: string): Promise<void>;
}
```

`selectMicrophone()` changes the in-memory preference. During an active call it
first acquires the replacement track, calls `RTCRtpSender.replaceTrack()`, and
stops the old track only after replacement succeeds. On failure the old track
continues and the promise rejects. While idle, selection is validated on the
next `prepare()` or call acquisition.

`setAudioOutput()` uses `HTMLMediaElement.setSinkId()` when available. It rejects
with `OUTPUT_SELECTION_UNSUPPORTED` when the capability is missing. It does not
pretend success, create elements, or swallow playback/output errors.

`attachRemoteAudio()` assigns the active remote stream to an application-owned
element, optionally selects an output, and calls and awaits `play()` only when
`play: true` is requested. A rejected `play()` maps to `PLAYBACK_FAILED`. It
returns an idempotent detach function and also detaches on session cleanup when
the element still refers to that session's stream. It never creates a DOM node
or treats autoplay rejection as successful playback.

There is one preparation method: `ua.media.prepare()`. A duplicate
`ua.prepareMedia()` convenience alias is deliberately not added.

### Browser media options

```ts
interface BrowserMediaOptions {
  readonly iceServers?: readonly RTCIceServer[];
  readonly iceTransportPolicy?: RTCIceTransportPolicy;
  readonly iceGatheringTimeoutMs?: number; // default 8 seconds
  readonly mediaOperationTimeoutMs?: number; // default 30 seconds
  readonly microphoneDeviceId?: string;
  readonly audioConstraints?: MediaTrackConstraints;
  readonly codecPreference?: readonly ('opus' | 'PCMU' | 'PCMA')[];
}
```

Timeout values must be finite, positive, and bounded by documented maximums.
Configuration is defensively copied so later application mutation cannot alter
an active negotiation. `iceTransportPolicy: 'relay'` is supported for TURN-only
deployments and relay verification.

`prepare()` accepts an `AbortSignal`. Browsers do not consistently support
cancelling a pending permission prompt, so cancellation invalidates the
operation; any stream delivered later is stopped immediately and cannot alter
state.

## State and Event Contract

A media session uses this monotonic state machine, with the documented ICE
restart loop from `connected` back through `negotiating`:

```text
new -> acquiring -> negotiating -> connecting -> connected
 |         |             |             |             |
 `---------+-------------+-------------+-----------> failed
                                                   |
any nonterminal state ---------------------------> closed
```

The public media events are:

- `mediaStateChanged`: session ID, previous state, next state, and safe reason
  code when applicable.
- `remoteAudio`: session ID and the session-owned remote `MediaStream`.
- `mediaFailed`: session ID and typed `MediaError`.
- `deviceChanged`: notification only; the application calls `listDevices()` for
  the current privacy-filtered list.

Core UA events and browser media events share one typed event surface. User
listeners are isolated so an exception cannot corrupt negotiation or cleanup.
No event contains SDP, ICE credentials, candidate addresses, raw constraints,
or unredacted device labels unless the application explicitly requested the
device list.

Exactly one initial offer/answer or re-INVITE negotiation may be active for a
session. Duplicate operations reject with `INVALID_STATE`; they are not merged
silently. Termination wins every race and causes pending operations to reject
with `ABORTED` after releasing late-arriving resources.

## Serializable Media Protocol

The core media protocol remains plain structured-clone-safe data. It is extended
to carry negotiation intent and typed safe errors:

```ts
type MediaCommand =
  | { type: 'createOffer'; requestId: string; sessionId: string;
      iceRestart?: boolean }
  | { type: 'createAnswer'; requestId: string; sessionId: string;
      remoteSdp: string }
  | { type: 'setRemote'; requestId: string; sessionId: string;
      remoteSdp: string }
  | { type: 'closeSession'; sessionId: string };

type MediaReply =
  | { type: 'mediaResult'; requestId: string; sessionId: string; sdp?: string }
  | { type: 'mediaError'; requestId: string; sessionId: string;
      code: MediaErrorCode; message: string };
```

The core package defines `MediaError` and a stable `MediaErrorCode` union:

- `PERMISSION_DENIED`
- `DEVICE_NOT_FOUND`
- `DEVICE_UNAVAILABLE`
- `CONSTRAINT_UNSATISFIED`
- `NEGOTIATION_FAILED`
- `REMOTE_DESCRIPTION_REJECTED`
- `ICE_GATHERING_TIMEOUT`
- `ICE_CONNECTION_FAILED`
- `OUTPUT_SELECTION_UNSUPPORTED`
- `PLAYBACK_FAILED`
- `ABORTED`
- `INTERNAL_ERROR`

Browser `DOMException` names are mapped at the browser boundary. The serialized
reply carries only a safe message and code; it never carries exception objects,
stacks, SDP, constraints, device IDs, candidates, or TURN data.

The controller reconstructs a `MediaError` rather than flattening every failure
to `MEDIA_UNAVAILABLE`. Unknown/malformed error replies map to
`INTERNAL_ERROR`. Existing request correlation, stale-reply rejection, and
session cancellation rules continue to apply. Browser composition configures
the controller deadline above the bounded browser operation so the more precise
browser failure normally wins.

## Initial Offer/Answer Flow

### Outgoing call

1. Core requests `createOffer(sessionId)`.
2. The manager reserves the sole active session and acquires a fresh selected
   microphone track.
3. The session creates one audio `sendrecv` transceiver and attaches the track.
4. Codec preferences are applied from browser capabilities without SDP text
   munging.
5. The session creates and applies the local offer.
6. It waits for `iceGatheringState === 'complete'` within the ICE deadline.
7. The complete local SDP is returned to core and sent in the SIP INVITE.
8. On a 2xx response, core sends `setRemote()` before confirming the media
   negotiation. A rejected remote description fails and tears down the call.

### Incoming call

1. Core creates an `Invitation` containing the opaque remote offer.
2. `invitation.answer()` requests `createAnswer(sessionId, remoteSdp)`.
3. The manager reserves the active session, acquires a fresh microphone track,
   creates the audio transceiver, validates and applies the remote offer, then
   creates and applies the local answer.
4. It waits for complete ICE gathering within the deadline.
5. Core sends 200 OK with the returned SDP and resolves `answer()` only under
   the existing ACK-confirmation contract.

For both directions, an ICE-gathering timeout fails closed and releases the
session; partially gathered SDP is not sent. A SIP cancellation or hangup that
races any step wins, and any subsequently delivered track is immediately
stopped.

The v0.5 SDP policy accepts one usable audio section and rejects unsupported
media changes with a typed error. It does not add video or data channels. Remote
SDP is size-bounded before being passed to the browser, and is never logged.

## ICE, TURN, and Re-INVITE

Non-trickle ICE is the only v0.5 signaling policy. The SDK does not advertise
SIP trickle-ICE support. This favors compatibility with ordinary SIP
offer/answer endpoints and avoids inventing an INFO/UPDATE candidate transport.

The application supplies `RTCConfiguration.iceServers`, including short-lived
TURN credentials where needed. The SDK supports UDP, TCP, and TLS TURN URLs to
the extent provided by the browser. It does not fetch, refresh, persist, or log
credentials. Applications must obtain renewed credentials before constructing
or reconfiguring calls when their deployment requires rotation.

`await ua.restartIce()` is valid only for a confirmed active call. It:

1. reserves the session negotiation lock;
2. invokes `createOffer({ iceRestart: true })` through the media protocol;
3. sends a serialized in-dialog re-INVITE with a monotonically increasing CSeq;
4. applies a successful remote answer;
5. resolves only when signaling and media negotiation have both succeeded.

Incoming in-dialog re-INVITEs containing a supported audio offer are routed to
the owning call, answered through the same serialized media path, and replied to
with complete non-trickle SDP. A re-INVITE that collides with local negotiation
receives 491 Request Pending. Unsupported media receives 488 Not Acceptable
Here. This milestone does not automatically retry glare or automatically start
ICE restart; those recovery policies belong to v0.7.

If restart signaling fails, the existing connection is not reported as
recovered. Whether it remains usable is reflected by browser ICE state; terminal
ICE failure produces `ICE_CONNECTION_FAILED` and call failure. There is no
silent success based only on sending the re-INVITE.

## Codec Policy

The browser's `RTCRtpSender.getCapabilities('audio')` output is the source of
truth. The SDK orders supported Opus first by default, followed by PCMU and
PCMA, while retaining browser-associated telephone-event entries for future
DTMF support. An application preference may reorder or narrow the named primary
codecs, but negotiation fails if no usable audio codec remains.

When `setCodecPreferences()` is unavailable, the SDK preserves browser order
and verifies that a usable codec remains instead of editing SDP text. Codec
matching is case-insensitive by MIME subtype and respects clock rate/channel
identity. The SDK does not claim to implement codecs itself.

## Remote Audio and Output Selection

The first remote audio track creates or joins the session's single remote
`MediaStream` and emits `remoteAudio`. Additional audio tracks for the same
session are incorporated deterministically without creating hidden elements.
Video and data tracks are outside scope and are not surfaced as supported media.

The application assigns the stream to its own media element and calls
`play()` from an appropriate user gesture. Autoplay rejection therefore remains
observable to product UI. A small renderer helper may attach/detach `srcObject`,
select an output, and optionally await `play()` as defined by the public API; it
must not create DOM nodes or claim playback before `play()` resolves.

Output selection is capability-gated. Because browser support and permission
policy differ, the support matrix states where `setSinkId()` is unavailable.
The default output always remains usable without calling this method.

## Lifecycle and Concurrency Rules

- One `BrowserUserAgent` permits one active or negotiating media session in
  v0.5. An outgoing call while busy rejects with `INVALID_STATE`; a second
  incoming call is rejected at SIP level with 486 Busy Here.
- `prepare()`, call acquisition, microphone replacement, initial negotiation,
  ICE restart, termination, and disposal each have explicit operation tokens.
- `closeSession` is idempotent and cancels every pending request for that
  session. Late media replies are ignored after their resources are reclaimed.
- Remote BYE, local BYE, CANCEL, rejected calls, ACK timeout, signaling failure,
  media failure, and UA disposal all converge on the same session cleanup.
- `BrowserUserAgent.dispose()` is idempotent. It stops accepting work, disposes
  core signaling, closes media sessions, removes `devicechange` listeners,
  closes media ports, and clears public listeners.
- The manager does not reuse a microphone track across calls. This prevents one
  call's teardown or constraint changes from corrupting another lifecycle.
- An active microphone replacement is transactional: acquire new, replace,
  commit selection, then stop old. Any earlier failure rolls back.

## Security and Privacy

- Media capture requires a secure context except browser-defined localhost
  development exceptions. The setup guide states this before the first example.
- WebRTC provides DTLS-SRTP media. No plain-RTP browser fallback exists.
- Remote SDP has a documented maximum byte size and media-section limit before
  browser parsing. Unsupported video/data behavior is rejected explicitly.
- SDP, ICE candidates, local/remote IP addresses, device IDs/labels, SIP
  credentials, and TURN credentials are sensitive and excluded from default
  logs and error messages.
- Browser media permissions are requested only by explicit `prepare()`,
  `invite()`, or `answer()` actions. Import, construction, connect, and register
  do not activate capture.
- Probe and call tracks are stopped on every success, failure, cancellation, and
  disposal path.
- The SDK does not persist device choices or credentials. Product applications
  that do so own consent, storage, rotation, and privacy policy.
- Media constraints and ICE configuration are treated as untrusted application
  input, validated, bounded, and defensively copied.

## Testing Strategy

### Deterministic tests

Injected media devices, peer connections, clocks, and ports cover:

- offer/answer ordering and one-transceiver construction;
- codec ordering and no SDP text munging;
- permission, device, constraint, SDP, ICE, timeout, and malformed-reply errors;
- operation cancellation and late track/SDP delivery;
- microphone replacement commit and rollback;
- initial negotiation and re-INVITE serialization, 491 collision, and 488
  unsupported-media handling;
- listener isolation and event ordering;
- repeated disposal and every SIP/media termination route;
- no retained tracks, connections, listeners, timers, or pending requests.

Core tests continue to use the media protocol and stub without requiring DOM
libraries. Browser unit tests own all WebRTC and media-device fakes.

### Real-browser media tests

Playwright runs Chromium, Firefox, and WebKit projects. A controllable peer
connection endpoint and synthetic audio source establish both directions
without relying on a human microphone. Tests assert:

- remote audio tracks arrive in both directions;
- RTP packet/byte counters increase in browser `getStats()`;
- an audio analyser observes non-zero synthetic signal where the engine permits
  stable analysis;
- direct and STUN-assisted calls complete;
- repeated calls and disposal return live peer-connection and track counters to
  zero.

Permission/no-device cases use deterministic injected media-device adapters,
plus browser permission smoke coverage where automation exposes reliable
controls. A test is not marked passed because a browser capability was skipped.
Declared output-selection exceptions are assertions against the published
support matrix.

Playwright WebKit is not treated as identical to shipping Safari. A mandatory
release job runs the packed package on current Safari on macOS. Missing runner
or service credentials fail the release prerequisite rather than producing a
successful skip.

### TURN relay test

A pinned coturn service is part of the provisioned integration environment. A
browser test uses `iceTransportPolicy: 'relay'`, establishes two-way audio, and
asserts from `getStats()` that the selected candidate pair uses relay
candidates. Merely verifying configuration propagation is insufficient.

TURN infrastructure is provisioned for the integration/release job rather than
silently made optional in the test. Credentials and logs are redacted in CI.

## Browser Support Policy for v0.5

The development matrix is Playwright Chromium, Firefox, and WebKit. Release
evidence adds current shipping Safari on macOS. Exact tested browser versions
are recorded in the release report rather than described only as "modern."

The broader current-and-previous Chrome, Edge, Firefox, and current Safari
support promise remains the v0.9 interoperability gate. v0.5 publishes its
narrower tested matrix and does not overstate Playwright engine evidence as a
full product support guarantee.

## Packaging and Documentation

The browser package adds public media exports at `sip-worker/media` and exports
`BrowserUserAgent` from the root. `@sip-worker/core` exports only serializable
media protocol/controller/error types. `@sip-worker/node` gains no WebRTC
implementation.

All packages publish at 0.5.0 with exact internal dependency versions. Existing
ESM, CommonJS, declaration, API-report, class-identity, browser-bundle, and
packed-artifact gates remain mandatory. Browser import audits reject Node
built-ins and import-time browser-global access.

Required v0.5 documentation:

- five-minute outgoing and incoming audio examples;
- HTTPS, WSS, microphone permission, autoplay, and Permissions Policy notes;
- STUN/TURN configuration with short-lived credential guidance;
- device selection and output-selection support behavior;
- media error-code and troubleshooting reference;
- migration from `Invitation.answer(localSdp)` to `answer()`;
- exact browser test matrix and known limitations;
- explicit statement that mute, hold, DTMF, automatic recovery, and certified
  PBX interoperability are not yet delivered.

## Explicitly Deferred

- Video, screen sharing, data channels, and conferencing.
- Mute/unmute, hold/resume, and DTMF public controls.
- Early media and reliable provisional response extensions beyond existing core
  behavior.
- Trickle ICE over SIP INFO, UPDATE, or proprietary signaling.
- Automatic ICE restart, browser network lifecycle policy, and TURN credential
  refresh.
- Multiple simultaneous active calls and call waiting.
- Production Node media.
- Final `BrowserPhone` v1 convenience API and credential-owning composition.
- Asterisk/FreeSWITCH certification, extended browser matrix, load, and soak
  evidence scheduled for v0.9.

These are explicit limitations, not implied completeness claims.

## Acceptance Gate

Version 0.5.0 is releasable only when:

1. Browser outgoing and incoming calls use real SDP and measurable two-way RTP.
2. Chromium, Firefox, WebKit, real Safari, and forced-TURN jobs pass using the
   packed browser artifact.
3. Permission denial, no device, unavailable device, invalid constraints,
   remote SDP rejection, ICE timeout/failure, cancellation, glare, unsupported
   output selection, and playback error behavior have typed assertions.
4. Microphone selection and transactional replacement pass success and rollback
   tests.
5. Local and remote ICE restart pass serialized in-dialog re-INVITE tests.
6. Repeated outgoing, incoming, rejected, cancelled, failed, remote-ended, and
   disposed calls leave zero owned tracks, peer connections, listeners, timers,
   and pending media requests.
7. Core remains DOM-free, browser remains Node-free, and importing packages has
   no environment side effects.
8. Full typecheck, unit, integration, architecture, API-report, bundle,
   compatibility, tarball, and migration-example gates pass without skipped
   required work.
9. The v0.5 release notes publish the exact browser evidence and limitations.

Only after this gate passes may the project describe v0.5 as real browser audio.
It must not yet describe the library as the completed v1 production product.
