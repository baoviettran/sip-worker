# 0.7.0 Browser Phone Call Controls and Recovery Review

## Scope

This review covers Milestone v0.7 (browser phone call controls and recovery) of
the `sip-worker` monorepo: the full product call-controls and recovery
milestone built on the v0.5 real-browser media foundation. It runs the
whole-milestone verification from a clean locked dependency tree, records
reproducible command evidence, and issues one explicit release verdict.

Review commits span the milestone base `782210e` (`docs: plan v0.7 call
controls and recovery`) through the review-remediated HEAD `53019be`
(`fix: resolve v0.7 review findings F1-F5 for call controls and recovery`):
22 commits, 111 files, 18,986 insertions, 745 deletions. The whole-milestone
review ran over `782210e..7ec1ed0`; its findings were remediated in `53019be`
and re-reviewed (see "Defects found and fixed by this review" below). A
follow-up commit `6bb84cf` (`fix(browser): resolve stale-complete ICE-restart
gathering`) fixes a library defect surfaced by the local forced-TURN gate and
records the final gate evidence (see "ICE-restart defect found and fixed"
below).

The milestone ships: bounded operation contracts with explicit
settlement/cancellation/deadline semantics; websocket generations and a bounded
reconnect policy; awaitable registration recovery; per-call ownership with
incoming/outgoing subtypes, CANCEL, and 486-busy; persistent call mute; RFC
3264 hold/resume with 491 glare handling; RFC 4733 DTMF; established-call
recovery (in-dialog OPTIONS validation or server-observed ICE-restart
re-INVITE); redacted diagnostics with an exact 11-counter `ResourceSnapshot`;
the public `BrowserPhone`/`BrowserCall` product surface; a packed-artifact
example softphone; and a real-browser acceptance seam
(`test/browser-phone`) across Chromium, Firefox, and Playwright WebKit.

## Public API summary

What v0.7 ships (from `etc/browser.api.md`, `etc/core.api.md`, and the
published contract in `docs/browser-phone.md`):

- `BrowserPhone` — the product composition root: `connect`, `register`,
  `unregister`, `disconnect`, `createCall`, `dispose`, typed events
  (`connectionStateChanged`, `registrationStateChanged`, `incomingCall`,
  `failed`), `diagnostics.resources()`, `diagnostics.onRecord`, and reconnect
  policy constants (`DEFAULT_RECONNECT_OPTIONS`, caps
  `MAX_RECONNECT_ATTEMPTS=20`, `MAX_RECONNECT_DELAY_MS=30000`,
  `MAX_RECOVERY_TIMEOUT_MS=120000`).
- `BrowserCall` + `OutgoingBrowserCall` / `IncomingBrowserCall` — `start`,
  `answer`, `cancel`, `reject`, `hangup`, `setMuted`, `hold`, `resume`,
  `sendDtmf`, `restartIce`, typed events (`stateChanged`,
  `signalingStateChanged`, `holdStateChanged`, `mutedChanged`,
  `mediaStateChanged`, `remoteAudio`, `mediaFailed`, `failed`).
- State unions `ConnectionState`, `RegistrationState`, `CallState`,
  `CallSignalingState`, `HoldState`; the 21-member closed `DiagnosticCode`
  telemetry union; nine new `SipErrorCode` members for the v0.7 reconnect /
  recovery / DTMF failures.
- RFC 4733 DTMF (upper-case `0-9 A-D *#`, both SDP sides negotiate
  `telephone-event`, never falls back to SIP INFO, duration 40-6000 ms default
  100, gap min 30 default 70).
- TURN: static `iceServers` or `iceServerProvider` with credentials validated
  and adopted on refresh.
- WSS is mandatory by default; `ws://` requires exactly
  `signaling.allowInsecureWebSocket: true`.
- The v0.5 `BrowserUserAgent` surface remains (migration map in
  `docs/migrations/0.5-to-0.7.md`); `Registrar.onTransportConnected()` was
  removed when registration recovery became awaitable.

## Defects found and fixed by this review

The whole-milestone review (`/superpowers:requesting-code-review`) ran the full
clean-tree verification, the three-engine browser gate, scans, and a diff audit
over `782210e..7ec1ed0`. It surfaced **2 Important + 3 Minor findings, plus 1
adjudicated observation**. Each code defect was first proven RED with a focused
failing regression (unit and/or real-browser), then fixed with the smallest
change, re-verified through the focused and affected browser gates, and
committed as `53019be` (`fix: resolve v0.7 review findings F1-F5 for call
controls and recovery`, 13 files, +420/−12) before being recorded here. A
re-review of the fix diff returned **APPROVE with no new findings**.

1. **F1 (Important) — remote re-INVITE re-acquired media and leaked the old
   track.** On an established call, a peer-initiated re-INVITE reached
   `MediaManager.owned!.createAnswer()` (media-manager.ts), which routed to
   `MediaSession.createAnswer`, which **unconditionally** re-ran
   `aquireTrackAndWire('negotiating')` → a second `addTransceiver` + a fresh
   local track written over `this.localTrack` **without stopping the old
   track**. Consequences: applied mute silently failed (the newly-acquired live
   track replaced the muted one), a live audio track leaked past mute/hangup,
   and the library ended up with two audio transceivers. **RED proven at both
   levels:** unit `session.test.ts` (second `createAnswer` pushes
   `transceivers.length` to 2 vs `toHaveLength(1)`) and real browser
   (`micAcquisitionsAfterReinvite` 2 vs 1). **Fix:** `session.ts:297-313`
   acquires/wires only when `this.transceiver === null`; a re-INVITE on an
   existing session reuses the existing transceiver/localTrack, so the applied
   mute/hold direction still governs the sent track. The fresh incoming-call
   path is unchanged and the error path (`releaseAfterFailure`) keeps its
   pre-fix contract. **Regression:** new `test/browser-phone/reinvite.spec.ts`
   (peer-initiated in-dialog re-INVITE on an established call) asserts one
   page-side `getUserMedia` acquisition, library transceiver count 1 before and
   after, unchanged sender track id, signaling `stable`, mute silences the wire
   (real inbound RTP bytes), unmute restores RTP, and the exact 11-key zero
   resource baseline; `test/browser-phone/server.mjs`, `index.html`, and
   `test/browser-media/synthetic-peer.ts` gained the in-dialog re-INVITE seam
   (relayed answer + ACK, advanced CSeq, reusing the `/control/hold-offers` and
   `/control/ice-restarts` recording endpoints; SDP bodies never logged).
   Unit regression in `session.test.ts` is load-bearing (fails with the fix
   reverted).

2. **F2 (Important) — docs overclaimed incoming-call hangup.** `IncomingBrowserCall.hangup()`
   rejects `INVALID_STATE`; inbound BYE ownership is a later-milestone item.
   Adjudicated **not** to implement inbound hangup in v0.7 (the plan does not
   contract it); `docs/browser-phone.md` now states the hangup bullet as
   outgoing-only with the `INVALID_STATE` caveat and v0.9 framing, and the
   migration/compatibility docs remain truthful.

3. **F3 (Minor) — `BrowserCall.mediaState` returned the constant `'new'`.** Now
   returns the real last-known `MediaSessionState` via `mediaStateValue`; the
   unit suite asserts `'connected'` after establishment.

4. **F4 (Minor) — `connectedSessions` was never pruned.** The runtime's Set only
   ever `.add()`ed; it now `.delete()`s on session close/failure. A reclaim test
   proves a reused session id no longer settles from a stale marker;
   `waitForMediaConnected`'s fast path is unaffected for live sessions.

5. **F5 (Minor) — `notifyMediaEvent` sessionId guard covered only
   `mutedChanged`.** Every media event branch now correlates by
   `event.sessionId === this.mediaSessionId` at the top of the handler (stale
   ignored, matching forwarded); the redundant inner check was removed.

6. **F6 (Observation, adjudicated — no change) — five pre-existing

## ICE-restart defect found and fixed (final gate run at `6bb84cf`)

Running the local forced-TURN gate surfaced a library defect in ICE-restart
gathering; it was proven RED, fixed, re-reviewed, and committed as `6bb84cf`
(`fix(browser): resolve stale-complete ICE-restart gathering`, 7 files,
+260/−29).

**Defect.** `waitForIceComplete` subscribed to `oniceconnectionstatechange`
*after* `setLocalDescription` and resolved on any `'complete'`. A re-INVITE ICE
restart therefore saw the **previous** generation's lingering `'complete'` and
resolved the waiter immediately — before the restarted gather produced any
candidates — leaving the library to answer with a candidate-less SDP. The
stale-complete regression (`it('does NOT resolve the ICE waiter on the stale
previous-generation complete')`) was written first and proven RED.

**Fix (RFC 8445 §9).** The waiter now discriminates ICE generations by ufrag:
`restartsIce = offeredUfrag !== null && currentUfrag !== null &&
offeredUfrag !== currentUfrag`; `freshGatherSeen` starts at `!restartsIce` and
is set when the state leaves `'complete'`; the waiter resolves only on
`complete && freshGatherSeen` (`session.ts`, `waitForIceComplete` plus the new
`iceUfragOf` helper, single-m-section by design with a future multi-media
note). The fake `FakePeerConnection.createAnswer` gained the RFC 8445 §9
credential model (the answerer mints fresh credentials only when the offerer
restarted its own, tracked via `previousRemoteUfrag`), and
`SyntheticPeer.gather()` gained the same ufrag guard against the stale
`'complete'`. F1 regression: `it('reuses answerer credentials on a
same-credential re-INVITE and mints fresh ones when the offerer restarts')`.

**Per-engine proof that the restarted path stays relayed.** Post-restart
`getStats` behavior differs by engine: Chromium and WebKit report a fresh
relay/relay pair; Firefox emits **zero** peer pair stats while RTP flows, so
its proof is resumed peer RTP over the library's relay pair
(`peerRelayPairAfterRestart === true ||
(peerRtpGrewAfterRestart === true && libraryRelayPairAfterRestart === true)` —
non-tautological: the RTP clause is asserted only in the Firefox branch).
Provider re-query (`providerCalls >= 2`) and credential re-application via
`setConfiguration` are asserted on the refreshed-provider path; value rotation
is unit-level in `manager.test.ts` (local coturn uses a fixed `-u user:pass`
list, an lt-cred-mech limitation documented in `test/browser-phone/index.html`).
