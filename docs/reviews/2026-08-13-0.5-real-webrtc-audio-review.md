# 0.5.0 Real Browser WebRTC Audio Review

## Scope

This review covers Milestone 3 (the v0.5 real browser WebRTC audio milestone): the
replacement of the fixed SDP media stub with real, two-way browser audio driven by a
`BrowserUserAgent` composition root over a serializable core media protocol. It is a
real-media foundation with bounded operations, deterministic ownership, typed
failures, real-browser tests, and no resource leaks — NOT a completed v1 softphone.
Mute, hold, DTMF, automatic network recovery, the final v1 API, and PBX
interoperability certification remain later roadmap milestones (see the design's
Explicitly Deferred section).

Review commits span the milestone base `85e26c4` through the evidence-recorded HEAD
(after the Task-15 commits below). The Task-14 milestone finished at `c97974e` with
the API/package/docs contract published and its packed-consumer evidence; the
Task-15 audit found and fixed four real defects (recorded in the Defects section),
then re-verified the complete chain from a clean dependency tree.

### Two-way RTP / audio assertions

Each `two-way-audio` case asserts from browser `getStats()`:
- library and peer both reach `connected`; ICE `connected|completed`; gathering complete;
- RTP packet and byte counters strictly increase on the library's outbound AND
  inbound and the peer's outbound AND inbound (all `> 0`);
- remote audio tracks arrive in BOTH directions (peer received the library's audio
  track and the library received the peer's audio track);
- selected local/remote candidate types resolve on the library's PC;
- after the clean close, live peer-connection/track/listener/timer/resources return
  to zero (`waitZeroResources`).

The `non-zero audio energy` test observes non-zero synthetic energy (OscillatorNode →
MediaStreamAudioDestinationNode with distinct frequencies per direction) on both
receiving sides, with every side required to either measure real energy or explicitly
admit a documented context limitation (e.g. Chromium headless-shell's
`null-audio-decode-sink`) — a side reporting silent-zero without admission fails.

## Security and Boundary Audit

- The one-call rule lives at the SIP layer (core `UserAgent`: a NEW incoming INVITE
  while busy is answered 486 Busy Here before any media acquisition) AND at the
  media layer (the browser `WebRtcMediaManager` enforces a single active/reserved
  media session, returning `INVALID_STATE`/duplicate rejection). A simultaneous call
  can never contend for the single media session.
- Import-time environment access: importing any public entry point (including
  `sip-worker/media`) touches no browser global. The `import-safety` gate replaces
  `window`/`document`/`navigator`/`RTCPeerConnection` with throwing sentinels and
  reports `boundary violations: 0 | side-effect violations: 0` over every target in
  both ESM and CJS.
- The lone executable-global AST exception is the dedicated lazy browser-media
  environment seam `packages/browser/src/media/error-mapper.ts`, which resolves
  globals only inside `createBrowserMediaEnvironment()`/per-call accessors (never at
  import). A new regression test proves the factory reads globals only when invoked.
- SDP, ICE candidates, local/remote IPs, SIP and TURN credentials, and device
  IDs/labels are excluded from default logs and from `MediaError` messages (fixed
  safe messages; the raw cause is retained only as a non-enumerable, non-serialized
  `localCause`).

## Migrated public API (Task 14, confirmed holding)

- `Invitation.answer()` now takes no `localSdp` argument (media applies the remote
  offer and creates the local answer internally). The migration guide
  `docs/migrations/0.3-to-0.5.md` calls this out as a pre-1.0 breaking change.
- New `BrowserUserAgent` + `ua.media` facade (`prepare`, `listDevices`,
  `selectMicrophone`, `attachRemoteAudio`, `setAudioOutput`), `restartIce`, typed
  coded `MediaError`/14-code union, and the `sip-worker/media` subpath.
- `docs/browser-media.md`, `docs/media-errors.md`, `docs/migrations/0.3-to-0.5.md`,
  `docs/compatibility/0.5-browser-media.md` all frame v0.5 as a real-media
  foundation, not completed v1 certification, and record exact tested versions and
  limitations.

## Defects found and fixed by this review

Four real issues surfaced during clean-tree verification. Each fix is a small,
focused change; the full chain re-passed afterward.

1. **Legacy core integration test contradicted the v0.5 one-call gate (test bug, seed).
   ** `packages/core/test/integration/call.test.ts` ("routes a BYE to its incoming
   dialog while an outgoing dialog remains active") still expected a fresh inbound
   dialog to be accepted while an outgoing call was confirmed. Commit 840ef87
   intentionally made a busy UA answer a NEW incoming INVITE with 486 before
   constructing an Invitation or acquiring media. Fixed the test to assert the
   v0.5 behavior: 486 Busy Here is sent, no `incomingCall` fires, the outgoing call
   stays confirmed.

2. **Two orphaned rejected promises failed `npm test` (unhandled-rejection leaks).**
   `user-agent.test.ts` and `browser-user-agent.test.ts` launched an in-flight
   `invite()` whose promise was discarded; on `disconnect()`/`dispose()` it rejected
   with `LIFECYCLE_ABORTED`, and vitest counted it as an unhandled error (run continued
   with "Errors 2" and exit 1 even though 842/842 passed). Fixed by consuming the
   promises before disconnect/dispose. This was the reason a fresh clean-tree verify
   flaked between exit 0 and exit 1.

3. **The executable-global AST gate over-reached the browser media seam (gate bug).**
   `test/architecture/import-boundaries.test.mjs` flagged bare `globalThis` reads in
   the single dedicated lazy environment seam. The seam is import-side-effect-free
   (the runtime `import-safety` gate proves it), so the exception is now narrowly
   scoped to that one file with a documented rationale, and a regression test in
   `error-mapper.test.ts` proves globals are read only on factory invocation.

4. **TURN gate infrastructure defects (fixed).** The provisioning script now
   leaves the healthy relay running for the browser step, accepts Linux loopback
   routing without interactive privilege escalation, cleans its exact container
   unconditionally, parses standard `turn:` URLs correctly, and enables loopback
   ICE in the local Firefox acceptance profile. The repaired gate passed all three
   Playwright engines.

## Remaining Limitations

These are inherited, unchanged, and out of scope for this milestone:

- No mute, hold, DTMF, video, screen share, data channels, or conferencing.
- No automatic ICE restart, browser network/lifecycle recovery, or TURN credential
  refresh (ICE restart signaling is explicit via `restartIce()` and re-INVITE; v0.7
  adds recovery policy).
- One active media call per `BrowserUserAgent` in 0.5.0; a second is rejected.
- No certified PBX interoperability (Asterisk/FreeSWITCH/Kamailio) evidence, and no
  broader browser matrix / load / soak evidence — those are the v0.9 gate.
- Forced-TURN relay passed locally across all three Playwright engines. The CI
  job now installs and runs all three engines as a required gate. Shipping-Safari
  evidence still requires the macOS CI workflow; v0.5 release readiness remains
  dependent on that green Safari run.
- Chromium's headless-shell decodes WebRTC audio to a null sink; the energy test
  honestly reports `null-audio-decode-sink` there (RTP bytes still flow and are
  asserted).

## Verdict

**RELEASE-READINESS: PENDING shipping-Safari evidence — implementationally complete.**

The complete v0.5 behavioral suite passes from packed artifacts in a clean
dependency tree (855/855 tests, no unhandled errors), the three real browser engines
(Chromium/Firefox/WebKit) demonstrate two-way real RTP audio, candidate-type proof
(host + STUN srflx), non-zero audio energy, and a 10-cycle lifecycle with zero leaked
PCs/tracks/listeners/timers/resources after every close; the API/package/docs gates
pass; and the redaction scan is clean. Fixes from the milestone review and
production remediation have focused regressions, and the full chain was
re-verified. The forced-TURN gate passed locally across all three Playwright
engines. Shipping Safari remains unverified and requires the macOS runner. Until
that workflow passes in CI, v0.5 is implementation-complete but not release-ready.
Record its run metadata and versions in the release notes when provisioned.
